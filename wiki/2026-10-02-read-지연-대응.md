## 배경

AWS r8 서버 로그(2026-10-02 03:15~03:33 UTC, 요청 30건, 합계 3969초)의 시간 구성:

| 단계 | 비중 | 중앙값 | 비고 |
| --- | --- | --- | --- |
| 대기+OCR | 27% | 28초 | p90 77초. PaddleOCR 레이아웃(L4)은 동시 2건에서 포화 |
| 표 교정(`TABLE_REFINE`) | 29% | 23초 | p90 96초, 최대 224초. 표 블록마다 순차 호출, 칸 수에 비례(2364칸 224초). 408 3건 모두 표 교정이 긴 요청 |
| 추출 | 14% | | |
| 재처리 루프 | 31% | 43초 | 최대 98초. 상한 60초를 진행 중 호출이 넘김 |

하네스는 같은 페이지에 필드 요청과 표 요청을 같은 X-Request-ID로 동시에 보내고, 두 요청이 OCR→표 교정→추출→재처리를 처음부터 따로 했다. 서버 시한 `READ_MAX_MS`는 180초인데 하네스는 300초까지 기다리고, 시한 검사가 단계 경계에서만 이뤄져 408이 184~278초에 났다.

모델 호출이 시한을 넘긴 원인: httpx `timeout`은 바이트 사이 간격만 잰다. OpenRouter는 응답 전까지 keep-alive 공백을 흘려 보내므로, 남은 시한으로 `timeout`을 잘라도 호출이 끝나지 않았다(로그: 남은 시간 약 80초에 시작한 1984칸 표 교정이 181초 걸리고 278초에 408).

## 변경

모두 `backend/latency.py`의 공용 장치(`shared`·`ocr_slot`·`parallel`·`track`/`timed`·`remaining`/`capped`)를 쓴다.

1. **같은 페이지 결과 공유** — `parsers.parse`가 원격 OCR(`provider="paddle"`) 결과를 이미지 바이트 해시와 OCR·표 교정 설정을 key로 프로세스 안에 잠시 기억한다(LRU). 같은 key가 계산 중이면 먼저 온 계산을 기다려 나눠 쓴다(single-flight). 실패한 계산은 기억하지 않고 기다리던 요청이 다시 계산한다. 호출자마다 사본을 준다.
2. **표 교정 병렬·분할** — `engine.refine_table`(블록 하나)을 `engine.refine_tables`(블록 목록)로 바꿨다. 칸이 `REFINE_MAX_CELLS`보다 많은 표는 행 단위 묶음으로 나누고(셀 번호는 표 전체 기준 그대로, 프롬프트에 "일부 행" 안내 추가), 모든 호출을 `REFINE_CONCURRENCY`개까지 병렬로 보낸 뒤 교정을 합친다. 호출마다 남은 시한을 상한으로 쓰고, 시한이 지나면 반쯤 교정된 결과를 남기지 않고 TimeoutError(408)를 낸다.
3. **GPU OCR 동시성 제한** — `_remote_paddle`의 레이아웃 호출(재처리 ROI 재OCR·회전 재OCR 포함)을 프로세스 전역 세마포어(`OCR_CONCURRENCY`)로 감쌌다. 자리를 기다리다 시한이 지나면 즉시 TimeoutError(408). 원격 timeout은 자리를 얻은 뒤의 남은 시한으로 자른다. 줄 OCR(`PADDLEOCR_LINES_URL`)은 제한하지 않고 timeout만 시한으로 자른다.
4. **재처리 시한 인식** — 남은 시간이 `REPROCESS_MIN_STAGE_MS`(단, `REPROCESS_MAX_MS`의 절반을 넘지 않음)보다 적으면 회전·ROI 재OCR·ROI/넓은 VLM 단계를 시작하지 않고 `stop_reason="deadline"`으로 멈춘다. 로컬 규칙 단계는 계속한다.
5. **시한 정합** — `engine._provider`가 응답을 스트림으로 받으며 벽시계로 남은 시한(`timeout_cap`)을 재어 넘으면 TimeoutError를 낸다. 시한이 없는 호출(문서 작업 경로)은 이전과 같다. `READ_MAX_MS`는 이미 환경변수이므로 코드 기본값(180초)은 그대로 두고 `.env.aws.example`에 권장값을 주석으로 적었다.
6. **단계별 시간 로그** — `read finished` 줄에 `ocr_ms ocr_wait_ms refine_ms extract_ms reprocess_ms cache_hit`를 붙였다. `ocr_ms`·`ocr_wait_ms`는 재처리 안의 재OCR도 더한 값이고, 공유 결과를 받은 요청은 `cache_hit=True`, `ocr_ms=0`이다.

정리: `reprocess._limit`을 `config.limit`으로 옮겨 새 설정과 함께 쓴다.

## 검증

- 단위 테스트 `tests/test_latency.py` 6건: 동시 같은 key 1회 계산·사본 공유·`cache_hit`, 실패한 선행 계산 뒤 재계산, OCR 자리 대기 중 시한 초과 TimeoutError(OCR 미호출), 분할 표 교정 병합 결과가 분할 없는 결과와 같음(호출 5회·칸 수 상한), 남은 시간이 적을 때 재처리 VLM 단계 미시작(`stop_reason=deadline`), keep-alive 공백이 흘러도 시한에 끊기는 모델 호출.
- 기존 테스트 조정: `refine_tables` 이름 변경, 테스트용 FakeClient에 `stream`, 10ms 시한에서 늦은 후보 폐기를 보는 테스트는 `REPROCESS_MIN_STAGE_MS=0`, conftest에 `READ_CACHE_SIZE=0`(같은 합성 이미지에 다른 OCR 응답을 모킹하므로).
- 전체 `pytest -q` 660 passed. AWS·외부 API 실측은 하지 않았다.

## 남은 위험

- 공유 key는 이미지 바이트 기준이다. 하네스가 두 요청에 다르게 인코딩한 이미지를 보내면 공유되지 않는다.
- 표 교정이 시한 외의 이유(HTTP 오류 등)로 일부 실패한 결과도 TTL 동안 공유된다(이전에도 그 요청은 교정 없는 결과를 썼다).
- 분할 호출은 표 전체 이미지를 매번 보낸다. 입력 토큰은 늘고, 행 묶음만 본 모델이 다른 행의 글자를 고칠 위험은 셀 번호 범위 밖 응답을 버리는 것으로만 막는다.
- 프로세스 안 캐시·세마포어라 워커를 여러 프로세스로 띄우면 프로세스마다 따로 센다.
- `REPROCESS_MIN_STAGE_MS=30000`은 재처리 60초 중 앞 30초에만 원격 단계를 연다. 재처리 채택률이 줄면 낮춘다. 효과는 다음 AWS 측정의 단계별 로그로 확인한다.

## 2026-10-02 추가 — `cache_hit` 오기록 수정 (브랜치 `fix/cache-hit-stat`)

AWS 1002i 로그에서 같은 요청 ID 쌍 17건 중 6건이 `cache_hit=False`로 남아 공유가 안 된 것처럼 보였다. 실제로는 17쌍 모두 표 교정(`refine_ms`)을 한쪽만 했다 — 공유는 동작했다. 재처리 루프의 크롭 재OCR도 `latency.shared`를 지나며 `cache_hit`를 마지막 값으로 덮어쓴 것이다. `note(..., add=None)`(처음 값만)로 바꿔 요청의 첫 호출(페이지 OCR) 결과만 남긴다. 참고: `ocr_ms`·`ocr_wait_ms`에는 재처리 크롭 재OCR 시간도 들어간다(페이지 OCR만 보려면 표 교정이 0인 쪽이 공유받은 요청).
