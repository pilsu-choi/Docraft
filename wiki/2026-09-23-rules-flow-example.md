# rules 후처리 흐름 예시 풀이

- 날짜: 2026-09-23 (2026-09-24 `rules.run` 반복 교정 기준으로 갱신)
- 브랜치: `fix/name-seal` → 갱신 `docs/rules-flow-doc`
- 워크트리: `.worktrees/name-seal` → 갱신 `.worktrees/rules-flow-doc`

`POST /api/verify`가 AO 결과를 어떻게 다시 읽고, 룰로 어디까지 고치고, 무엇을 Judge에 넘기는지 예시 입력으로 따라간다. 아래 출력은 모두 실제 실행 결과다(재현 스크립트는 맨 아래).

## 한 줄 요약

AO가 낸 답안을 Docraft가 **따로 한 번 더 읽고**, 둘을 비교해 **확실히 틀린 것은 룰로 바로 고치고**, 애매한 것만 **LLM Judge**가 이미지를 보고 판정한다. AO와 Docraft가 같게 읽은 값은 LLM에 보내지 않고 `source: "agree"`로 확정한다.

## 전체 흐름 (`verify.run`)

```
 이미지 + AO JSON
      │
 ① 파싱        PaddleOCR → 텍스트·표·좌표 블록
 ② 추출        engine.extract: 문서유형 스키마 + 블록 + 이미지 → VLM 값
 ③ 추출 후처리  rules.apply: 정규화·빈칸 채우기·표 정리 ─▶ Docraft 결과(AO를 재는 기준자)
      │
 ④ 룰 검사     rules.check: AO 값에서 이상 징후(flag) 찾기     ┐ rules.run
 ⑤ 룰 교정     확실한 것(CORRECT)만 AO 값을 직접 수정          ┘ 고칠 것이 없어질 때까지 최대 3회
      │
 ⑥ Judge      AO≠Docraft 필드 + 남은 flag(hint)만 LLM 1회 호출
 ⑦ 마무리      _balance 합계식 보조 → 남은 ESCALATE 이상은 review: true
      │
 AO와 같은 구조 + ao_value·docraft_value·source·reason, verify.trace
```

`apply`는 채점(`scripts/verify_eval.py`)에서도 쓰고, `derive`는 라벨 정리(`scripts/verify_label.conform`)에서도 쓴다. 추론·채점·라벨이 같은 규칙을 공유한다.

## 추출 (②③)

### ② VLM 추출 — `engine.extract`

- 스키마는 프로젝트 스키마가 아니라 문서 유형별 고정 스키마(`doctypes.py`)다.
- 프롬프트에 표 **근거 제약**(`doctypes.GROUND_HINT`, `engine.TABLE_NOTE`)을 붙인다: 인쇄된 행만 인쇄 순서대로, 인쇄되지 않은 표준 항목 행을 덧붙이지 않고, 이름을 표준 이름으로 바꿔 부르지 않는다.

### ③ `apply` 단계 순서

| # | 함수 | 하는 일 |
|---|---|---|
| 1 | `_value` | kind별 정규화 → `_junk`로 라벨·HTML 잔재 제거 → `FIELD_RULES` 정제 → enum 동의어 매핑 |
| 2 | `_serials` | 등록번호 칸의 연번호·발행번호 값을 차트번호로 옮김 |
| 3 | `_fill` | 빈 스칼라를 `LABELS` 동의어로 블록에서 찾아 채움(근거 등급·영역·배타 필터, 값이 하나로 모일 때만) |
| 4 | `_notes` | 소견 문장·`날짜 (검사)` 표시로 치료·검사·수술 내역 행 생성 |
| 5 | `_split_cells` | 병명 칸의 KCD 코드, 수술명 칸의 수술일자를 제 열로 분리 |
| 6 | `_receipt_table` | 진료비영수증 항목 행을 파서 표로 복원·보충, 열 밀림 되돌림 |
| 7 | 합계 정리 | 인쇄되지 않은 급여 합계 비움(`UNPRINTED_NULL`) → `_totals`가 합계 행으로 빈 합계 필드 채움 → 구성 합과 다른 급여총액 비움 |
| 8 | `_header_columns` | 머리글로 보아 서식에 없는 금액 열(묶음 제목 등) 비움 |
| 9 | `_swap` | 진료비영수증에서 통째로 맞바뀐 이웃 금액 열을 합계 행에 맞춰 되돌림 |
| 10 | `_period` | 진료기간을 표 시작·종료일자로 채움 |
| 11 | `derive` | 표 열 관례, 주민번호 → 성별·생년월일, 외래/입원, 사고발생일자 |
| 12 | `_master_names` | 코드가 마스터에 있을 때만 명칭 1글자 오인식 교정 |

## 룰 검사·교정 (④⑤) — `rules.run`

`rules.RULES`에 룰마다 검사(`detect`)·교정(`fix`)·실패 시 조치(`on_fail`)·교정 순서(`priority`)가 등록되어 있다.

| on_fail | 의미 | 대표 룰 |
|---|---|---|
| `CORRECT` | 룰이 직접 고친다 | `RECEIPT.ROW_SHIFT`, `RECEIPT.COLUMN_SWAP`, `RECEIPT.COLUMN_SHIFT`, `RECEIPT.ITEM_NAME`, `RECEIPT.ROW_MISSING`, `DETAIL.ITEM_CLASS`, `SUM.FIELD`·`GROUND.UNPRINTED`(급여 합계 비우기) |
| `RE_EXTRACT` | 고치지 않고 Judge에 hint로 넘긴다 | `SUM.TABLE`, `DATE.ORDER`, `ID.MISMATCH`, `RECEIPT.ROW_EXTRA`, `RECEIPT.ROW_COPY`, `DETAIL.ROW_ARITH` |
| `ESCALATE` | 끝까지 남으면 `review: true` | `MISSING.REQUIRED`, `DETAIL.LOW_QUALITY` |

교정 순서는 행 밀림(-2) → 열 통째 맞바뀜(-1) → 칸 이동·급여구분·합계(0) → 이름(1) → 행 끼우기(2)다. 한 회차에 고친 뒤 다시 검사하고, 고칠 것이 없거나 앞선 상태로 되돌아가면(진동) 멈춘다. 회차별 룰 결과는 `verify.trace`에 남는다.

## 예시 A. 진단서 — `apply`

입력 ① VLM 원본

```json
{"이름": "홍길동 (인)", "환자 주민번호": "900101-1234567", "성별": "성별",
 "진단일": "2026. 9. 1", "발급일": "2026년 09월 05일",
 "병원명": "명칭: 서울정형외과의원(직인)", "진료과": null,
 "병명내역": [{"병명": "요추 염좌 (S33.5)", "병명코드": null}]}
```

입력 ② OCR 파서 블록

```
표:  | 환자 | 성명 | 홍길동 |  /  | 진료과목 | 정형외과 |
텍스트: "치료소견: 요추부 통증으로 물리치료 및 약물치료 시행함"
        "2026.09.03 (검사)"
```

| 단계 | 필드 | 전 | 후 | 이유 |
|---|---|---|---|---|
| `_value` | 진단일 | `2026. 9. 1` | `20260901` | date → YYYYMMDD |
| | 발급일 | `2026년 09월 05일` | `20260905` | 표기가 달라도 같은 형식 |
| | 병원명 | `명칭: 서울정형외과의원(직인)` | `서울정형외과의원` | `_hospital`이 라벨·직인 제거 |
| | 이름 | `홍길동 (인)` | `홍길동` | `_name`이 도장 표시 제거 |
| | 성별 | `성별` | `null` | `_junk`: 값 자리에 라벨 글자 → 버림 |
| `_fill` | 진료과 | `null` | `정형외과` | 표의 `진료과목` 셀(동의어) 오른쪽 값 |
| `_notes` | 치료내역 | — | `[{치료명: "요추부 통증으로…시행함"}]` | `치료소견:` 뒤 10자 이상 문장. 날짜는 과거력일 수 있어 비움 |
| | 검사내역 | — | `[{검사일: 20260903, 검사명: 검사}]` | `날짜 (검사)` 표시 |
| `_split_cells` | 병명내역 | `요추 염좌 (S33.5)` | 병명 `요추 염좌`, 코드 `S335` | 코드 분리(비교용 정규형이라 점 제거) |
| `derive` | 성별 | `null` | `남` | 주민번호 뒷자리 첫 숫자 `1` |
| | 생년월일 | — | `19900101` | `1` → 1900년대 + `900101` |

`_value`에서 라벨 글자 "성별"을 버렸기 때문에 `derive`에서 주민번호로 올바른 값이 채워진다. "틀린 값보다 빈칸이 낫고, 빈칸은 근거가 있으면 채운다"는 설계가 이렇게 맞물린다.

## 예시 B. 진료비영수증 — `run`(검사·교정 반복) → Judge

실제 인쇄 내용: 진찰료 5,000/10,000, 주사료 0/0, 투약및조제료_행위료 15,000/20,000, 합계 20,000/30,000(본인부담금/공단부담금), 진료비총액 50,000.

AO 결과에는 오류 네 가지를 넣었다.

```
진료비총액 58000                                     ← ❶ 숫자 오독
진찰료                본인 10000 / 공단 5000         ← ❷ 본인·공단 열이 통째로 맞바뀜
투약 및 조제료 행위료  본인 20000 / 공단 15000        ← ❸ 비표준 항목명
합계                  본인 20000 / 공단 30000
                                                      ← ❹ 주사료(0원) 행 누락
```

Docraft는 VLM 원본 `"50,000원"`, `"투약 및 조제료 행위료"`를 `apply`로 `50000`, `투약및조제료_행위료`(`item_aliases`)로 다듬어 인쇄 내용과 같게 읽었다.

### 1회차 검사

```
SUM.FIELD            진료비총액 58,000이 환자부담총액+공단부담총액 50,000과 다르다.        → ❶
RECEIPT.ROW_MISSING  Docraft가 읽은 항목 '주사료' 행이 AO 표에 없다.                       → ❹
RECEIPT.COLUMN_SHIFT 0행 '진찰료'의 '본인부담금' 값이 Docraft의 '공단부담금' 값과 같다(×4)   → ❷
RECEIPT.ITEM_NAME    '투약 및 조제료 행위료'은 '투약및조제료_행위료'로 적는다.              → ❸
SUM.TABLE            합계 행 본인부담금 20,000 ≠ 항목 합 30,000, 공단부담금 30,000 ≠ 20,000 → ❷의 증상
SUM.TABLE            진료비총액 58,000 ≠ 합계 행 금액 합 50,000                             → ❶
RECEIPT.COLUMN_SWAP  '본인부담금'·'공단부담금' 열을 통째로 맞바꾸면 두 열의 합이 합계 행과 맞는다. → ❷
MISSING.REQUIRED     발행일·의료기관정보 등이 비어 있다(예시에서 뺀 필드)
```

### 1회차 교정

```
[RECEIPT.COLUMN_SWAP] 항목 행의 본인부담금·공단부담금 열을 맞바꿨다
[RECEIPT.ITEM_NAME]   투약 및 조제료 행위료를 투약및조제료_행위료로 고쳤다
[RECEIPT.ROW_MISSING] 금액이 모두 0인 '주사료' 행을 Docraft에서 채웠다
```

| 이상 | 룰 교정 | 이유 |
|---|---|---|
| ❷ 열 맞바뀜 | 고침 | 합계 행은 맞고 두 열의 합만 서로 바뀌어 있어, 맞바꾸면 두 열이 모두 정확히 맞는다 |
| ❷ 같은 원인의 `COLUMN_SHIFT` | 중복 교정 안 함 | `COLUMN_SWAP`(-1)이 먼저 고쳐 옮길 자리가 이미 차 있다 |
| ❸ 항목명 | 고침 | 별칭 규칙이 하나의 표준 이름을 가리킨다 |
| ❹ 주사료 누락 | 고침 | 금액이 전부 0이라 끼워도 합계를 해치지 않는다. 자리는 Docraft 순서대로 진찰료 뒤 |
| ❶ 총액 오독 | 안 고침 | 합계식이 틀린 것은 알지만 총액과 구성 금액 중 어느 쪽 오독인지 모른다(`RE_EXTRACT`) |

### 2회차 검사

열·이름·행 flag는 모두 사라지고 `SUM.FIELD`·`SUM.TABLE`(진료비총액)과 `MISSING.REQUIRED`만 남는다. 더 고칠 것이 없어 반복이 끝난다.

### Judge와 합계 보조

교정된 `항목내역`은 이제 Docraft와 같아 disputes에서 빠진다. Judge에는 진료비총액 하나만 간다.

```json
{"진료비총액": {"ao": "58000", "docraft": "50000",
               "hint": "진료비총액 58,000이 환자부담총액+공단부담총액 50,000과 다르다. ..."}}
```

Judge가 흐린 숫자에 속아 `ao`(58000)를 골라도 `_balance`가 합계식을 다시 본다. 58000이면 불일치가 1건, Docraft 값 50000이면 0건이므로 50000으로 되돌리고 `reason`에 그 사유를 남긴다.

### 최종 응답(요지)

```
진료비총액   value 50000, ao_value 58000, source "docraft"
항목내역     rows 교정본, source "corrected", reason "[RECEIPT.COLUMN_SWAP] … / [RECEIPT.ITEM_NAME] … / [RECEIPT.ROW_MISSING] …"
환자부담총액 value 20000, source "agree"   ← 둘이 같아 LLM 없이 확정
```

## 원칙

- Docraft는 AO를 재는 기준자이지 덮어쓸 정답이 아니다. 룰은 두 근거 이상이 같은 곳을 가리킬 때만 고친다(예: `ROW_SHIFT`는 Docraft와 파서 표가 모두 그 행에서 값을 읽었을 때만 옮긴다).
- "틀렸다"는 알지만 "무엇이 맞는지" 모르면 고치지 않고 hint로 Judge에 넘긴다.
- 룰 데이터(동의어·합계식·별칭·필수 필드·`disable`)는 `backend/rulesets/rules.yaml`, 로직은 `backend/rules.py`에 둔다.

## 찾은 버그와 수정 (2026-09-23)

예시 A를 돌리는 중 `이름: "홍길동 (인)"`이 `"홍길동인"`이 되는 것을 발견했다. `_name`은 한글 외 글자만 지우고 `_NAME_WORDS`에 도장 표시 `인`이 없어서 남았다. 이름 안의 `인`(김인수·이인)은 지키고, 괄호 속 `(인)`·`[인]`·`(印)`과 이름 뒤에 떨어진 `인` 토큰만 도장 표시로 지우도록 고쳤다. 회귀 테스트를 추가했다.

## 재현 스크립트

```python
from backend import rules
vlm = {"이름": "홍길동 (인)", "환자 주민번호": "900101-1234567", "성별": "성별",
       "진단일": "2026. 9. 1", "발급일": "2026년 09월 05일", "병원명": "명칭: 서울정형외과의원(직인)",
       "진료과": None, "병명내역": [{"병명": "요추 염좌 (S33.5)", "병명코드": None}]}
blocks = [{"rows": [["환자", "성명", "홍길동"], ["진료과목", "정형외과"]],
           "text": "치료소견: 요추부 통증으로 물리치료 및 약물치료 시행함\n2026.09.03 (검사)"}]
print(rules.apply("진단서", vlm, blocks))

T = "진료비영수증"
docraft = rules.apply(T, {"진료비총액": "50,000원", "환자부담총액": "20,000", "공단부담총액": "30,000",
    "항목내역": [{"항목": "진찰료", "본인부담금": "5,000", "공단부담금": "10,000"},
                {"항목": "주사료", "본인부담금": "0", "공단부담금": "0"},
```
