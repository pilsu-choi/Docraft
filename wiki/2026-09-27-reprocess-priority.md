# 자동 재처리의 근거·규칙 우선순위

날짜: 2026-09-27
브랜치: `feat/reprocess-priority`
워크트리: `Docraft/.worktrees/reprocess-priority`

## 동작

문서 전체에 공유되는 기본 4회 시도를 필드 삽입 순서 대신 근거와 규칙 관계로 배분한다. 우선순위는 **정확한 OCR 줄 위치와 규칙 관계**, **정확한 OCR 줄 위치**, **근사 OCR 줄 위치**, **위치가 약한 규칙 관계**, **나머지 검토 필드** 순이다. 같은 순위에서는 기존 필드 순서를 유지한다. 실제 OCR 줄의 페이지·좌표·원문 일치를 요구하므로 표 전체나 블록 상자만 맞는 값은 위치가 확인된 것으로 다루지 않는다. 표 셀은 원문 행·열 연관도 필요하다. `row_conflict`, `row_mismatch`, 먼 라벨 등 충돌이 있으면 강한 위치 근거로 올리지 않는다.

규칙의 필드 key가 단일 값이나 표의 특정 행·열을 가리킬 때만 직접 위반으로 연결한다. 직접 위반이 있는 `PASS`도 `SUSPICIOUS`/`RECHECK` 대상으로 올리며, 후보의 위반이 실제로 사라지고 기존 근거·의미·회귀 검사를 통과해야 채택한다. 행 또는 표 전체에만 붙은 규칙 플래그는 그 범위의 **기존 검토 필드** 순서만 올린다. 임의 셀을 위반으로 확정하거나 정상 셀을 강등하지 않는다. `trace`의 `select` 단계는 선택 이유 코드를 기록한다. 선택 순서 외 재처리 4단계, 기본 추가 모델 2회, 60초 제한, 근거 없는 필드의 fallback 기회와 후보 채택 문턱은 유지한다.

## 검증과 한계

단일 필드 규칙의 잔존·해소, 앞쪽 출처 없는 필드보다 뒤쪽 원문 위치·규칙 위반 필드의 선행, 블록 상자 오인 방지, 표 행·열·셀 플래그의 적용 범위, 동순위 순서와 예산을 회귀 시험으로 확인했다. 전체 회귀 580개가 통과했다. OCR 줄 일치는 이미지의 참값을 뜻하지 않는다. 행·표 전체 규칙에서 어느 셀이 실제 원인인지 확정할 수 없으므로 해당 셀의 자동 `CORRECTED`를 주장하지 않는다. 문서 공유 예산이 소진되면 뒤 필드는 여전히 미처리될 수 있다.

독립 35건의 기존 원본 중 진단서·영수증·세부내역서 각 1건을 같은 초기 Parse·Extract 캐시에서 재생했다. 기본 예산(4회·추가 모델 2회)에서 진단서는 기존과 같은 근거 부족 필드, 영수증은 `공단부담총액`·`진료비총액`, 세부내역서는 `항목내역/0/총액`의 규칙 관련 필드가 먼저 선택됐다. 세 문서 모두 채택은 0건이었다. 따라서 **대상 순서 변경은 확인됐지만 정확도 개선은 관찰되지 않았다**. 진단서 원본 대조에서는 체크 표시가 실제로 보이지만 추출 결과가 Y/N이라 OCR 기호와 문자열이 일치하지 않았고, 입원일도 원문 날짜 표기와 추출값 형식 차이로 `no_source`가 됐다. 해당 캐시 블록에는 OCR `lines`가 없어 새 강한 위치 우선순위를 부여할 수 없었다. 출처 판정을 완화하거나 표시·날짜를 임의 변환하는 변경은 이번 우선순위 작업에 포함하지 않았다.

세부내역서 원본 대조에서는 별도 `사고발생일자`란이 없고 스키마가 진료 시작일의 의미상 별칭으로 정의한다. `환자정보(진료시작일/종료일)`은 인쇄된 단일 `진료기간` 범위를 나눈 값이어서 각각의 정확한 OCR 원문 연결이 없었다. `급여_본인부담총액`은 병합 머리글과 총계행 때문에 같은 열의 데이터·합계 후보가 겹치며 캐시에는 줄 좌표가 없어 표 전체 bbox만 남았다. 이는 후속 출처 연결·스키마 정책 검토 과제이며 우선순위만으로 정상 근거가 생기지는 않는다.

영수증 원본 대조에서는 `외래입원`, `공단부담총액`, `발행일`의 추출값이 silver 라벨과 같지만 OCR 캐시에 정확한 원문 근거가 없었다. 반면 `상한액초과금`은 원문 빈칸인데 추출값이 있어 실제 오류였다. 캐시의 표 2개를 포함한 6개 블록에는 OCR 줄 좌표가 없고, 일부 총액·발행일 숫자는 OCR 텍스트에도 없다. 빈칸을 확인해 `null`로 고치는 작업은 현재 후보 채택 계약의 범위 밖이다. 이처럼 재처리 우선순위는 출처 누락과 실제 오독을 분리하지 못한다.

확대 예산(8회·추가 모델 4회·90초)으로 같은 3건을 다시 재생해도 채택은 모두 0건이었다. 진단서는 임상적 추정·최종 진단·입원일, 영수증은 규칙 관련 총액 3개, 세부내역서는 첫 행 총액·사고발생일자·진료 시작일 순으로 시도됐다. 이는 뒤쪽 필드에 기회를 더 줘도 기존의 원문 연결·후보 검증 한계가 해소되지 않았음을 보여준다. 확대 예산은 실험 조건이며 운영 기본값은 4회·2회·60초로 유지한다.

## 요청과 배경

[이전 자동 재처리 구현](2026-09-27-auto-reprocess-loop.md)의 자연 표본 3건에서는 앞쪽 원문 근거 부족 필드가 공용 시도 예산을 소진해 교정 채택이 없었다. 원문 위치가 확인된 의심 필드와 실제 규칙 위반 필드를 먼저 처리하도록 개선한다.

## 범위

기존의 근거 검증·원값 보존·문서별 60초/4단계/추가 VLM 2회 상한을 유지한다. 우선순위와 선택 이유를 명확히 하고, 채택 기준을 완화하거나 표본 라벨을 변경하지 않는다. Sol이 구현·보고 도구를 분담하고 Luna가 위치 근거와 규칙 매핑을 독립 검토한다.

## 검증 계획

서로 다른 우선순위, 동률의 안정적 순서, 표 셀과 중첩 경로의 규칙 매핑, 호출 상한·정상값 보존을 확인한다. 동일 캐시의 자연 표본 3건에 실제 AWS OCR와 VLM 재처리를 적용해 이전 trace와 처리 대상을 비교한다. 값 변경 교정과 값 그대로 근거만 개선한 채택을 구분하며 실제 정확도 향상은 독립 라벨 비교가 뒷받침할 때만 표시한다.

## 추가 요청: 예산 확대의 효과 분리

사용자가 기존 자연 표본에서 예산만 늘리면 해결되는지 확인을 요청했다. 동일 초기 캐시와 문서 3건에 대해 기존 순서/개선 순서 × 기본/확대 예산을 비교한다. 기본은 60초·4단계·VLM 2회, 확대는 90초·8단계·VLM 4회다. 확대는 현 서버 상한 안의 시험용 설정이며 운영 기본값은 바꾸지 않는다. 초기 Parse·Extract를 재실행한 전체 API E2E가 아니라 실제 OCR/VLM을 사용하는 재처리 replay다. 기존 기본 결과는 `Docraft/data/verify/auto-reprocess-20260927/smoke-final.jsonl`의 이전 측정값이며, 측정 시점·모델 응답 변동 가능성이 있다.

## 원문 대조: 진단서 근거 연결 실패

사용자의 추가 원인 조사 요청에 따라 표본 0의 원본 이미지를 직접 확인하고 초기 OCR·추출 캐시와 비교했다. 개인값은 이 기록에 남기지 않는다.

- 임상적 추정·최종진단은 체크형 항목이다. 원본에는 체크 표시가 있고 OCR 블록에도 체크 기호가 있지만, 스키마 출력은 `Y/N`이다. 현 근거 매칭은 선택 상태를 해당 표시 영역에 연결하지 못해 `no_source`로 남는다. 문서에 항목이 없어서 실패한 사례가 아니다.
- 입원일은 원본과 OCR에 인쇄되어 있다. `rules._dates_in`으로 비교하면 추출값과 일치하지만, 추출값의 `YYYYMMDD`와 OCR의 한국어 년·월·일 표기를 `engine._needles`가 동등한 원문으로 찾지 못한다.
- 이 항목들이 든 캐시 블록에는 OCR 줄 좌표(`lines[].bbox`)가 없다. 라벨 존재·값 의미 일치와 개별 필드 좌표 확보는 별도의 문제다.

이번 변경은 선택 우선순위이며 체크 표시·날짜 변환의 증거 규칙을 새로 구현하지 않는다. 위 제약을 근거 없는 값을 채택하도록 완화해서 우회하지 않는다.

## 예산만 확대한 결과

기존 순서에서 기본→확대 예산으로 비교했을 때 세 건 모두 값 교정 채택은 0건이었다. 실행 시간은 진단서 9.8→15.2초, 영수증 3.5→10.2초, 세부내역서 2.7→7.9초였다. 확대 실행은 각각 추가 VLM 4·4·3회, 모두 8단계에서 중단했다. 더 뒤쪽 필드를 시도했으나 원문·라벨 연결 실패와 모호한 근거가 계속되어, 이 표본에서는 예산 확대만으로 해결되지 않았다.

## 우선순위 개선 기본 예산 결과

개선 코드에서 영수증은 외래/입원 대신 공단부담총액·진료비총액 규칙 위반을 먼저 선택했고, 세부내역서는 사고발생일자 대신 첫 행의 총액 규칙 위반을 먼저 선택했다. 진단서는 강한 위치 근거와 규칙 위반이 없어 기존 fallback 순서를 유지했다. 세 건 모두 값 변경/동일값 근거 개선 채택은 0건이다. 실행 시간은 각각 11.0·27.2·17.6초였다. 더 유망한 대상으로 순서를 바꾸는 기능은 확인했지만 정확도 개선을 입증한 결과는 아니다.

## 원문 대조: 영수증·세부내역서

Sol·Luna 에이전트가 원본 이미지를 직접 열어 확인하고 초기 OCR/추출 캐시·기존 silver 라벨과 대조했다. 라벨은 생성하거나 수정하지 않았다.

- 영수증의 외래/입원·공단부담총액·발행일은 추출값이 기존 silver 라벨과 정확히 같았으나 OCR 원문 근거가 연결되지 않았다. 관련 캐시는 6개 블록·표 2개, OCR 줄 좌표 0개다. 공단 총액·발행일의 실제 인쇄값이 해당 파싱 텍스트에 빠졌고, 발행일은 명시 라벨 없이 의료기관 하단에 인쇄되어 있다.
- 영수증의 상한액초과금(스키마 key `상환액초과금`)은 원본의 해당 칸이 공란인데 비공란 값이 추출된 실제 오류였다. 위 합계 행과 구분하고 빈칸 근거를 표현해야 한다. 현 루프는 근거 없는 null 후보를 채택하지 않으므로 예산 확대만으로 해결할 수 없다.
- 세부내역서에는 `진료기간` 아래 날짜 범위가 있으며 개별 시작일·종료일 라벨은 없다. 범위를 두 값에 연결하는 근거 규칙이 빠져 있다.
- 같은 서류에 별도 사고발생일 라벨은 없으며 현재 스키마가 진료 시작일과 같은 의미로 정의한다. 직접 인쇄 근거와 파생·별칭 근거를 구별해야 한다.
- 급여 본인부담총액은 `본인부담액` 아래 `급여` 하위열과 총계 행으로 식별해야 한다. 데이터 행과 총계 행에 같은 값이 있어 현 매칭이 모호해졌고, 캐시에는 표 블록 좌표만 있고 줄 좌표가 없다. 병합 머리글·총계 행 판별이 필요한 사례다.

이 조사로 기존 경보에는 실제 오추출과 맞는 값의 근거 연결 실패가 섞여 있음을 확인했다. 체크 선택 상태·날짜 정규화·범위 분할·표 셀/총계·빈칸 표현을 연결하는 후속 과제이며, 단순히 근거 검증을 느슨하게 만드는 해결책은 아니다.

## 개선 순서의 확대 예산 결과

8단계·VLM 4회·90초로 늘려도 세 건 모두 값 교정·동일값 근거 개선 채택은 0건이었다. 진단서 14.2초/4회, 영수증 56.5초/3회, 세부내역서 17.1초/4회였으며 모두 8단계에서 종료했다. 영수증은 공단부담총액·진료비총액·환자부담총액, 세부내역서는 첫 행 총액을 우선 처리했다. 우선순위 변경은 적용됐지만 근거 연결과 빈칸 계약 문제가 남아 결과 채택으로 이어지지 않았다.

## 검증

Docraft 전체 580개 테스트가 통과했고, 마지막 column-only 규칙 범위 보완 후 우선순위 전용 5개도 재실행해 통과했다. 명시적 leaf 규칙만 품질 상태를 변경하며, 행·열·표 단위 규칙은 해당 범위의 기존 의심 필드 선택에만 사용한다. 동률 순서는 유지하고 강한 위치에는 유효한 원문 줄 좌표를 요구한다. 원문 줄에 정합된 approximate 후보도 나머지 fallback보다 먼저 시도한다. 모델·시도 예산과 후보 검증 기준은 유지했다.

실측은 3개 문서를 네 조건으로 replay한 결과이며 서로 독립된 12개 문서 평가가 아니다. 모든 실행에서 초기 Parse·Extract 캐시는 재사용했다. 샘플 보고의 라벨 비교는 기존 loose 동치(금액의 null/0 동치 포함)이며 gold 성능 지표가 아니다. 이번에는 값 변경이 0건이라 정답 개선을 주장할 근거도 없다.

영수증 추가 대조에서 grounding `_labels`는 네 필드 모두 인쇄 라벨 앵커를 잡지 못했다. `rules.LABELS`에 공단부담금·상한액초과금 별칭이 있어도 grounding 단계가 이 별칭을 사용하지 않는다. 따라서 좌표 추가만으로 충분하지 않으며 공통 라벨 의미 연결이 함께 필요하다.
