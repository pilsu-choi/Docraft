# OCR 엣지 케이스 개선 우선순위: 속도와 정확도

- 날짜: 2026-09-25
- 브랜치: `docs/edge-speed-accuracy`
- 워크트리: `.worktrees/edge-speed-accuracy`
- 기준: `main`의 2026-09-25 코드와 [카탈로그 점검](2026-09-25-ocr-edge-catalog-audit.md), 기존 평가 기록. 아래 개선 효과는 **예상**이며 해당 작업을 구현해 실측한 결과가 아니다.

## 판단에 쓰는 기준선

- 57건 e2e는 **진료비영수증 29·세부내역서 28**에 한정된다. AO 단독→AO+Docraft 최신 기록은 영수증 96.19→98.16%, 세부내역서 95.52→96.73%다 ([210장 계획](2026-09-24-e2e-210-plan.md)). 다른 5종의 같은 경로 e2e 지연·정확도는 없다.
- `/api/verify`는 57건 실행별 평균 **103·120·154초**, 중앙값 96·106·148초였다. 공유 서버 부하와 모델 재실행 흔들림이 있으므로 한 번의 전후 실행에서 몇 초·몇 칸 차이만으로 채택하지 않는다 ([210장 계획](2026-09-24-e2e-210-plan.md)).
- 자동 통과 칸 정확도는 세부내역서 **99.71%(76.2% 통과)**, 영수증 **99.11%(81.5% 통과)**였다. AO confidence 임계값 0.9·0.95·0.98 추가는 불일치 조건보다 분리에 도움이 되지 않았다 ([auto-review](2026-09-24-auto-review.md)).
- AWS L4 레이아웃 OCR은 동시 요청 **2**에서 처리량이 포화했고, 전체 파이프라인은 `QUEUE_CONCURRENCY=6`에서 약 **10건/분**이었다. 동시성을 더 높이는 것은 우선 작업이 아니다 ([aws-throughput](2026-09-22-aws-throughput.md)).
- 현 `.env`·`.env.example`·AWS 예시는 `qwen/qwen3-vl-32b-instruct`다. 과거 같은 parse·라벨 76건에서 `qwen/qwen3.5-27b`는 정확도 **−2.4%p**, 추출 지연 약 **1.5~3배**였다. 이 기록만으로 현재 모델을 다시 바꿀 이유는 없다 ([model-compare](2026-09-23-label-alignment-and-model-compare.md)).

### 1. 먼저 고칠 값싼 오류

[auto-review](2026-09-24-auto-review.md)는 영수증 자동 통과 오류 중 **18칸이 출력 그룹 위치**, **8칸이 두 판독의 같은 항목명 오독**이라고 분류했다. 이는 추론량을 늘리기 전에 고칠 수 있다. 세부내역서에서는 파서 헤더를 못 찾아 `DETAIL.EMPTY_CELL`이 작동하지 않아 투여량을 비우는 사례가 남았다. 이미 일부 보완 후 실측 오류 수가 달라졌으나 실행마다 흔들렸으므로 동일 입력/모델 캐시와 새 실행을 분리해 검증한다 ([e2e-edge-cases](2026-09-24-e2e-edge-cases.md)).

규칙은 OCR 원문이나 파서 셀 근거가 있는 경우만 값을 바꾸고, 인쇄가 애매한 `병실=외래` 같은 값은 보류한다. 이것이 처리 시간을 크게 늘리지 않으면서 정확도를 올릴 가능성이 가장 높은 작은 작업이다.

### 2. 모델 호출을 줄일 때의 안전 조건

현재 `verify.run`은 문서마다 Paddle 파싱 뒤 `engine.extract`를 호출한다. AO와 Docraft가 다른 표는 `_row_diff`로 셀 차이를 찾지만, Judge 응답 계약은 **표 전체 행을 다시 반환**하게 한다 ([verify.py](../backend/verify.py)). 긴 세부내역서에서 답변 길이·행 재작성 위험이 있으므로 변경 셀만 반환하게 하고, 미변경 셀은 서버가 원본에서 보존하는 설계를 먼저 시범 적용한다. 적용 전후 `source=corrected`·`unknown`·`review`와 행 수를 함께 봐야 한다.

기존 [룰 1차 계획](2026-09-22-verify-rule-first-plan.md)은 모델 추출 10~30초 제거를 예상했다. 이는 2026-09-22의 4건 환경 기록이며 최신 57건의 전체 103~154초와 직접 합산해 절감률로 주장할 수 없다. 먼저 영수증/세부내역 일부로 시범을 돌려 **폴백까지 포함한** 실제 절감과 오답을 측정한다. 소견서처럼 자유서술이 많은 유형은 초기 적용 대상에서 뺀다.

`TABLE_REFINE`·줄 OCR을 일괄 끄거나 AO confidence만으로 Judge를 생략하면 정확도 위험이 있다. 끄더라도 유형·헤더 검출·인쇄 근거를 확인한 경우에 한하고, 공통 오독(두 판독이 같이 틀림)을 놓치는지 `agree_wrong`으로 측정한다. 동시성 증가는 이미 측정된 레이아웃 포화 뒤라 후순위다.

### 3. 모델 변경과 이미지 전처리

모델 선택은 현재 32B 기준을 유지하며, 변경 제안은 76건 비교와 57건 e2e의 **같은 배포·라벨·parse**에서 다시 시험할 때만 한다. 사고 모드는 이미 기본 `off`다. 서버 설정이 달라졌는지는 실행 로그로 확인한다.

PaddleOCR의 공식 문서에는 문서 방향 분류와 기하 왜곡 보정을 선택적으로 켜는 전처리 파이프라인이 있다 ([PaddleOCR 공식 문서](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/doc_preprocessor.html)). 이 기능의 공개 모델 지연은 현 서비스의 왕복 지연이 아니므로 실제 배포 경로에서 재측정한다. 정상 스캔까지 일괄 재OCR하지 않고 방향·품질 실패 신호가 있는 이미지에만 사용한다.

## 실험 채택 기준

같은 문서와 검수된 정답을 고정하고 기존/후보를 문서별로 짝지어 비교한다. 반복 실행 편차가 확인됐으므로 후보별 최소 2회, 문서별 델타와 신뢰구간 또는 변동 폭을 함께 낸다. 기록할 지표는 유형/카탈로그 ID별 정확도·strict·오탐·누락, S1 자동 오확정 건수, 자동 통과 비율, review/HITL 비율, parse/extract/Judge 호출 수·토큰·p50/p95 지연, 총 처리량이다. **S1 자동 오확정이 늘거나 해당 유형의 정확도가 악화되는 속도 개선은 채택하지 않는다.**

## 후속: 모델 호출 없이 추가할 룰 후보

사용자 질문(2026-09-25)에 따라, 이미 구현된 `RECEIPT.ROW_SHIFT`·`RECEIPT.COLUMN_SHIFT`·`DETAIL.ROW_ARITH`·`SUM.FIELD` 등과 구별해 **새로 보완할 부분**을 골랐다. `자동 보정`은 인쇄 근거와 해석이 유일한 경우만 허용한다. `검출`은 `review`만 붙이고 값을 바꾸지 않는다.

| 우선 | 카탈로그 ID | 후보 룰 | 처리 | 비용·주의점 |
| --- | --- | --- | --- | --- |
| 1 | RCP-003, 세부내역 표 헤더 오류 | 영수증 표준 항목명에서 한 글자 누락/오독을 **유일한 표준명**으로만 고치고, 세부내역은 파서 머리글·셀 위치로 `투여량` 열의 인쇄 여부를 다시 판정 | 조건부 자동 보정 | CPU 위주. 유사 이름이 둘이면 보류. 현재 `RECEIPT.ITEM_NAME`·`DETAIL.EMPTY_CELL`의 실패 범위만 확장한다. |
| 2 | NRM-006, RCP-006 | 금액 셀 전체가 `(3,000)`처럼 괄호 숫자인 경우만 `-3000`으로 변환 | 자동 정규화 | 거의 0의 추가 지연. 설명 괄호가 붙은 숫자까지 음수로 바꾸지 않도록 전체 문자열 일치가 필요하다. 현재 `_amount`는 앞의 `-`·`△`만 음수로 본다. |
| 3 | RCP-004, INV-RCP-04 | 세 인쇄값이 모두 있을 때 `납부할금액 = 환자부담총액 − 이미납부한금액` 검산 | 검출 | `field_sums`에 이 관계가 없다. 중간정산·환불·서식별 정의가 달라 보이면 예외 처리하고, 어느 금액을 바꿀지는 자동 결정하지 않는다. |
| 4 | ADM-004, INV-ADM-01; DGN-005 | `기재 입원일수`·`발병일` 필드를 먼저 추가하고 날짜 차이 ±1일, 발병≤진단≤발행을 검사 | 검출 | 계산은 거의 무료지만 누락 필드를 읽는 스키마 작업이 선행된다. 불일치 시 인쇄값을 보존한다. |
| 5 | XDC-003/005/008/009/013, CMN-018 | 청구 묶음 안에서 기간·총액·코드 상위 접두·수술일, 동일 바이트 해시/영수증 번호를 비교 | 검출; 완전 동일 파일의 중복 OCR은 캐시 재사용 가능 | CPU 비교는 저렴하나 `claim_group_id`와 기간 동일/발췌 여부를 알아야 한다. 기간 다른 세부내역과 중간정산은 합계 불일치로 단정하지 않는다. 같은 금액·날짜만으로 청구 중복 자동 삭제는 금지한다. |

`DTL-006`의 단가×투여량×횟수×일수와 약제비 합계식은 이미 검출한다. 여기에 새 산식을 더하더라도 **한 셀의 정답이 유일하게 인쇄된 것이 아니면** 숫자를 역산해 덮지 않는다. `-`를 무조건 0으로 바꾸거나, 비어 있는 체크박스를 false로 바꾸는 규칙도 서식 의미가 달라 오확정 위험이 있다. 자유서술의 부정·불확실 표현, 수술/시술 약관 판단, 가려진 글자 복원은 단순 룰의 자동 확정 대상으로 두지 않는다.
