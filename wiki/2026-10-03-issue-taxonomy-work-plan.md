## 단계

### 0. 기준 고정: 기계 판독 레지스트리

- 분류 트리를 `taxonomy.yaml` 한 곳에 둔다. 항목은 ID·이름·부모·정의·버전·폐기 시 대체 ID다. 문서의 트리는 이 파일에서 만들거나, 둘이 같은지 검사한다.
- 검사 스크립트: ID가 겹치지 않는지, 문서·작업지시서·프로파일이 참조한 ID가 레지스트리에 있는지, 폐기된 ID를 쓰고 있지 않은지 본다. 이번 개정 때 손으로 돌린 검사를 상시화하는 것이다.
- ID를 바꿀 때는 폐기 표시와 대체 ID를 남기고, 기존 이슈 기록은 지우지 않는다.

### 1. 단계별 값 기록: 귀속의 전제

- 필드마다 parse값 → 추출 원값 → 재판독값 → 후처리 각 변경(어떤 규칙이 무엇을 무엇으로) → 최종값의 순서를 기록한다.
- 일반 메커니즘: 값을 바꾸는 모든 지점이 공통 기록 함수를 거치게 한다. 특정 규칙에만 기록을 붙이지 않는다.
- 고객 출력 계약은 바꾸지 않는다. 내부 trace·감사 기록에만 남긴다.
- 이 기록이 있어야 `AUX.POST.*`를 판정할 수 있고, "최종 출력만으로 원인을 확정하지 않는다"는 원칙을 지킬 수 있다.

### 2. 자동 1차 분류기

정답과 출력을 비교해 노드 후보를 자동으로 붙이고, 판정할 수 없는 것만 사람에게 넘긴다. label_viewer의 정렬·셀 상태를 재사용한다.

| 판정 신호 (문서 유형 무관) | 부여 후보 |
|---|---|
| 정렬 후 정답 있음·출력 없음 / 출력 있음·정답 없음 / 둘 다 있으나 다름 | `MIS` / `OVR` / `WRG` |
| 틀린 값이 같은 문서 다른 위치의 정답과 일치 | `E.WRG.ASSIGN.*` |
| 같은 행·열에서 같은 방향·폭의 배정 오류가 반복 | 오류 패턴 `일괄 밀림` |
| 앞 단위 누락 뒤로 배정 오류가 이어짐 | 오류 패턴 `연쇄` |
| 빈값 ↔ 0·미표기 차이 | `E.WRG.NORM.3` |
| 출력값이 원문 글자에 없고 다른 출력값들의 산식 결과와 일치 | `E.OVR.GEN.2` |
| 스키마 허용 목록·형식·필드 간 제약 위반 | `E.CON.RANGE.*` |
| 근거 위치가 다른 필드 근거와 겹치거나 값과 불일치 | `E.CON.EVID.3` |
| 중간 단계 값은 정답인데 최종값이 오답 | `AUX.POST.*` (변경한 규칙 유형으로 세분) |
| 중간 단계 값이 원문 표기와 다르고 정답은 원문 유지 | `E.WRG.NORM.4` / `AUX.POST.NORM` |
| 행 정렬 신뢰도가 낮거나 정답지 내부 불일치 | `AUX.EVAL` 의심 |

- 출력: 이슈 기록 jsonl. 원인 사건 ID, 영향 단위, 분류 ID 후보, 기록 축 값(오류 패턴·자동 탐지 여부·심각도·귀속 확실성)을 담는다.
- 사실 속성 해석(`ATTR`), 문맥 연결(`CTX`), 문서 경계(`DOC`)처럼 신호만으로 정할 수 없는 노드는 "사람 판정" 큐로 보낸다. 자동 판정 범위는 판정 정확도를 표본으로 확인한 뒤 넓힌다.

### 3. 기존 결과 재분류와 커버리지 지도

- 정답이 있는 결과(59건, 205건, 검수가 끝난 테스트셋)에 1차 분류기를 돌리고 사람 판정 큐를 처리한다.
- 노드 × 문서 유형 행렬을 만든다. 칸마다 관측 수, 자동 탐지율, 심각도 분포를 넣는다.
- 관측 0건 노드는 사유를 나눈다: 해당 문서·조건이 데이터에 없음 / 탐지하지 못해 안 보임 / 이 시스템 구조상 생기지 않음.

### 4. 빈 노드 채우기: 테스트 데이터

- 관측 0건 노드에 대해 실데이터(진단서·소견서 등 7종 테스트셋)에서 해당 조건 문서를 찾거나, 합성 작업지시서 v2의 변형 연산자에 노드 ID를 연결해 만든다.
- 합성 라벨의 `taxonomy` 필드는 0단계 레지스트리로 검사한다.
- 진단서·소견서는 `ATTR`, `P.STR.REL.3`(라벨·값 짝짓기), `P.STR.HIER`처럼 표 문서에서 드러나지 않는 노드의 주요 근거가 된다.

### 5. 런타임 탐지 메커니즘

- 노드마다 하네스가 실행 중에 의심을 표시할 수 있는지 정하고, `자동 탐지 여부` 축을 개선한다.
- 우선순위는 `심각도 상 × 자동 탐지 못함 × 관측 빈도`로 정한다. 근거 없는 수치 목표는 두지 않는다.
- 후보 메커니즘(모두 문서 유형 무관): 값 제약 검사(`RANGE`), 근거 무결성·겹침 검사(`EVID`), 일괄 밀림 탐지(행·열 단위 배정 오프셋), 계산값 의심(원문 글자 부재 + 산식 일치), 원문 대비 변환 감시(과정규화), 검증 통과만으로 확정하지 않는 근거 등급(`AUX.POST.VALID`).

### 6. 유형 단위 수정과 회귀

- 수정은 노드(문제 유형) 단위로 하고, 노드별 회귀 세트(실데이터 + 합성 변형)를 붙인다.
- AWS 확인은 dev push 후 배포 담당 세션에 요청한다. 직접 배포·호출하지 않는다.
- 완료 보고에는 근본 원인, 노드와 일반화 범위, 함께 처리한 사례, 추가한 테스트를 넣는다.

## 순서와 병렬화

| 순서 | 작업 | 병렬 |
|---|---|---|
| 1 | 0단계 레지스트리·검사 스크립트 | 단독(이후 모든 단계의 기준) |
| 2 | 1단계 하네스 단계별 기록 / 2단계 분류기 골격(정렬·신호) | 둘은 저장소가 달라 병렬 |
| 3 | 2단계에 단계별 기록 연결 → 3단계 재분류·커버리지 지도 | 순차 |
| 4 | 4단계 테스트 데이터 / 5단계 탐지 메커니즘 | 노드별로 병렬 |
| 5 | 6단계 수정·회귀 | 노드별 브랜치, 배포는 묶어서 |

## 결정이 필요한 것

1. **레지스트리 위치**: 하네스·label_viewer·합성 생성기가 함께 읽는다. 후보는 harness-v2 `rulesets/shared/`, 별도 공유 디렉터리, 상위 `mirae-assets` 중 하나다.
2. **분류기 위치**: label_viewer 백엔드 확장(사람 판정 화면을 함께 쓸 수 있음) 또는 하네스 평가 도구.
3. **7종 테스트셋 검수**: 사람 검수가 0건이라 3·4단계의 실데이터 근거가 막혀 있다. 검수 범위와 일정을 정해야 한다.
4. **단계별 기록 범위**: 기록량과 저장 비용. 전체 필드를 상시 기록할지, 평가 실행에서만 켤지 정한다.

## 자체 점검: 특정 사례에 맞춰진 부분

- 분류기 판정 신호와 탐지 메커니즘은 문서 유형과 무관한 형태로 적었다. 다만 실제 근거 데이터가 지금은 의료비 표 문서뿐이라, 3단계 첫 커버리지 지도는 표 관련 노드에 치우칠 것이다. 이 치우침은 결과가 아니라 데이터 공백으로 표시한다.
- 단계별 기록(1단계)은 하네스 구조(AO·Docraft·규칙 중재)를 전제로 구현하지만, 기록 형식은 "단계 이름·입력값·출력값·변경 주체"로 일반화해 다른 파이프라인에도 쓸 수 있게 한다.
