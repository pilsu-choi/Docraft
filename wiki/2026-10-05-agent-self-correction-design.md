## 1. 목적

지금은 사람이 정답지를 검수하고, 틀린 칸을 찾아 보정 규칙을 고친다. 이 설계는 그 일을 둘로 나눈다.

- **에이전트가 하는 일:** 오류 찾기, 다시 읽기, 근거 맞춰 보기, 유형 분류, 보정안 만들기, 회귀 확인
- **사람이 하는 일:** 정책 결정, 기준 정답 확정, 병합 승인

목표는 [이슈 유형 체계](2026-10-03-parse-extract-issue-taxonomy.md)가 정한 것과 같다. 아직 발견하지 못한 사례가 들어와도 보정 성능이 떨어지지 않아야 한다. 그래서 자가교정의 단위도 사례 하나가 아니라 **유형 칸**(출력 단위 × 차이 종류)이다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 실행 고리 | 운영 중 문서 한 건을 처리하면서 값을 고칠지 정하는 과정. 사람과 에이전트 개입 없이 정해진 규칙으로 동작한다 |
| 개발 고리 | 쌓인 실패를 모아 규칙·선언·코드를 고치는 과정. 에이전트가 브랜치를 만들고 사람이 병합을 승인한다 |
| 근거 | 값이 맞다고 볼 이유. 원문 인쇄, 다시 읽기, 여러 칸 합계, 한 칸 계산, 마스터, 추론의 6종 |
| 독립 근거 | 다른 근거와 출처가 겹치지 않는 근거. 같은 판독기에서 나온 근거 둘은 하나로 센다 |
| 기준 정답 | 합성 생성기가 문서를 만들 때 함께 확정한 정답 중, 사람이 검수 우선순위 상위부터 확인한 것. 채점 기준으로 고정하고 에이전트는 수정할 수 없다 |
| 합성 7종 세트 | 문서 7종(소견서·수술확인서·약제비영수증·입퇴원확인서·진단서·진료비세부산정내역서·진료비영수증)을 합성 생성기로 만든 평가 세트. 자가교정의 채점 기준이다. 정답지 59건은 이 설계에서 쓰지 않는다 |
| 예비 개발 브랜치(`pre-dev`) | 에이전트 보정안이 자동으로 병합되는 브랜치. 사람이 확인한 뒤 dev로 올린다 |
| 숨긴 검증셋 | 보정안을 만드는 에이전트가 볼 수 없는 문서 묶음. 점수 합계만 알려준다 |
| 노드 재현 표본 | 합성 생성기가 유형 칸마다 만든 오류본과 대조본 쌍. 정답을 알고 만든 문서다 |
| 관문 | 보정안이 병합 후보가 되기 위해 통과해야 하는 검사 |

## 3. 지켜야 할 원칙

다음은 이미 사용자와 고객사가 결정한 내용이다. 자가교정은 이를 바꾸지 않고 자동으로 지키는 장치다.

1. **원문 우선.** 원문과 달라지는 값은 근거가 확실할 때만 넣고, 그렇지 않으면 표시만 한다([원문과 달라지는 보정 금지](/home/pilsu/.claude/projects/-home-pilsu-projects-mirae-assets/memory/feedback-no-reference-correction.md)).
2. **인쇄된 값만.** 계산으로 채우는 것은 정책으로 허용한 칸에서만 한다. 지금 허용된 칸은 세부내역서 합계 급여총액(칸 없는 서식)뿐이다([소계 행 정책](2026-10-03-summary-rows-policy-integration.md), [인쇄되지 않은 값 열](../../wiki/2026-10-04-unprinted-column-copy.md)).
3. **판단은 하네스 한 곳.** Docraft는 판독 서비스다. 실행 고리의 값 결정은 하네스 판정 규칙표가 한다.
4. **일반화 우선.** 특정 문서·서식 코드·필드명을 하드코딩하지 않는다. 서식 지식은 `rulesets/shared/schema.yaml` 선언으로 둔다.
5. **채점 기준 불변.** 테스트 기대값이나 정답을 현재 출력에 맞춰 바꾸지 않는다.
6. **AWS 호출은 배포 담당 세션만.** 개발 고리는 로컬 재생으로 돌리고, AWS 확인은 묶어서 한 번만 요청한다.

빈 곳은 다섯 가지다.

1. 다시 읽기 결과가 하네스 판정에 독립 근거로 들어가는 길이 정해져 있지 않다. ④'는 등급이 애매한 문서만 처리하고, ③'는 Docraft 어댑터일 때 건너뛴다.
2. Docraft 응답 캐시가 없어서, 다시 읽기 경로를 로컬에서 재생할 수 없다.
3. **기준 정답이 없다.** 정답지 59건은 AI 초안이고, 이 설계에서는 쓰지 않는다(2026-10-05 사용자 결정). 대신 합성 7종 세트를 만들어 기준으로 삼는다. 합성 정답은 생성할 때 확정되지만, 정답 작성 정책이 실제 판정 정책과 맞는지는 사람이 확인해야 한다.
4. 보정안을 만드는 쪽과 채점하는 쪽이 분리되어 있지 않다. 지금은 같은 세션이 둘 다 한다.
5. 실패를 유형 칸에 모으고 보정안과 회귀 확인으로 잇는 순서가 사람 손에 있다.

## 5. 전체 구조

```
 ┌──────────────── 실행 고리 (문서 한 건, 운영 중, 결정형) ────────────────┐
 │ AO 결과 → ① 오류 찾기 → ② 대상 칸만 다시 읽기(Docraft, 1회)               │
 │        → ③ 근거 장부 작성 → ④ 값 결정표 → ⑤ 반영 또는 표시 → 변경 기록    │
 └──────────────────────────────┬──────────────────────────────────────────┘
                                │ 기록: 애매·미해결 칸, 변경 내역, 근거 충돌
                                ▼
 ┌──────────────── 개발 고리 (여러 문서, 주기 실행, 에이전트) ───────────────┐
 │ 수집 → 분류(유형 칸) → 재현(합성 변형) → 보정안(브랜치)                    │
 │      → 채점(고정 기준, 별도 에이전트) → 심사(일반화·금지 사항)             │
 │      → [사람] 병합 승인 / 정책 결정                                         │
 └─────────────────────────────────────────────────────────────────────────┘
```

두 고리는 서로 역할을 나눈다. 실행 고리는 이미 있는 장치 안에서 확실한 것만 고친다. 개발 고리는 그 장치 자체를 넓힌다. 실행 고리에는 LLM 에이전트를 넣지 않는다. 운영 결과는 다시 돌려도 같아야 하고, 변경마다 근거를 설명할 수 있어야 하기 때문이다.

## 6. 실행 고리 설계

### 6.1 오류 찾기: 다시 읽을 칸 고르기

다음 중 하나라도 걸린 칸을 대상으로 삼는다. 모두 이미 있는 장치의 출력이라 새 탐지기는 만들지 않는다.

| 신호 | 출처 |
|---|---|
| 원문 없음, 복제 의심, 추측 확정 | 원문 대조 `grounding` |
| 열 모양 이상, 행 밀림, 열 맞바뀜, 행 중복 | 표 구조 일관성 |
| 형식·범위·합계·날짜 선후 위반 | 스키마 선언 검사, 규칙 엔진 CALC |
| 등급 `ambiguous`·`unresolved` | 판정 규칙표 |
| 쪽 순서 이상, 같은 쪽 두 번 | Docraft 무결성 |

문서당 대상 칸에 상한을 둔다(설정값, 처음에는 20칸). 상한을 넘으면 칸 단위가 아니라 문서 전체 검토로 넘긴다. 칸이 그만큼 많으면 서식 오분류나 입력 손상일 가능성이 크기 때문이다.

### 6.2 다시 읽기: 1회, 범위 제한

- `POST /api/read`에 대상 칸의 `keys`와, 표라면 `row_filter`를 넣어 한 번 호출한다. 영역 API를 새로 만들지 않는다. 행·칸 지정으로 범위가 충분히 좁혀지고, Docraft 내부에서 이미 자기 bbox로 잘라 다시 읽기 때문이다(`reprocess._box`·`_crop`).
- 남은 시간은 `remaining_ms`로 넘기고, 동시 요청은 기존 `DOCRAFT_MAX_CONCURRENCY`를 따른다.
- **다시 읽기는 문서당 한 번이다.** 결과가 또 어긋나도 다시 부르지 않고 표시로 끝낸다. 두 판독기가 번갈아 서로를 고치는 왕복을 막기 위해서다.
- 이미지가 없는 경로(동기 API)에서는 이 단계를 건너뛴다. 근거 장부는 원문 대조와 합계만으로 쓴다.

### 6.3 근거 장부와 독립성

칸마다 후보 값(AO 원값, 다시 읽은 값, 계산값)과 각 값의 근거를 남긴다. 기존 `change_records`의 근거 종류 5개에 "여러 칸 합계"를 더해 6종으로 쓰고, 근거마다 **출처 묶음**을 붙인다.

| 근거 | 출처 묶음 | 혼자서 값 변경 가능? |
|---|---|---|
| 원문 인쇄 (AO parse 글자에 그 값이 있음) | AO | 아니오. AO 값과 출처가 같다 |
| 다시 읽기 (Docraft가 같은 값을 읽음) | Docraft | 아니오 |
| 여러 칸 합계 (서로 다른 칸 3개 이상이 함께 맞음) | 산식 | 예. 10/04 측정에서 이 근거만으로도 거의 맞았다(가드를 켜면 1칸 개선, 78칸 악화) |
| 한 칸 계산 | 산식 | 아니오 |
| 마스터 대조 | 마스터 | 아니오. 고객사가 염려한 사항이다 |
| 추론 | 없음 | 아니오 |

**독립 근거 수 = 서로 다른 출처 묶음 수.** AO 원값과 원문 인쇄는 같은 묶음이고, Docraft 다시 읽기는 다른 묶음이다.

### 6.4 값 결정표

| 상황 | 행동 | 등급 |
|---|---|---|
| AO 원값에 위반 신호가 없음 | 그대로 | `pass` |
| 후보 값에 원문 인쇄 근거와 다른 묶음의 독립 근거가 1개 이상 있고, AO 원값에는 독립 근거가 없음 | 후보로 바꿈 | `repaired`, 위치 이동이면 `swap` |
| 후보 값에 여러 칸 합계 근거만 있음 | 후보로 바꿈 | `repaired` (10/04 측정을 반영한 예외) |
| 후보 값이 원문에 인쇄되어 있지 않음 (계산 채움) | 정책 허용 칸이면 바꾸고, 아니면 표시만 | `inferred` 또는 `ambiguous` |
| 후보끼리 독립 근거 수가 같음 (충돌) | AO 원값 유지, 두 값 모두 기록 | `ambiguous` |
| 어떤 후보에도 근거가 없음 | AO 원값 유지 | `unresolved` |

**"원문 인쇄 + Docraft 다시 읽기 일치"를 충분한 근거로 볼 때의 조건 (2026-10-05 사용자 결정: 충분한 근거로 인정).** 두 근거가 정말 독립이려면 다음을 모두 지켜야 한다. 하나라도 어기면 근거 하나로 센다.

1. **답을 알려주지 않는다.** 다시 읽기 요청에 AO 값이나 후보 값을 넣지 않는다. `/api/read`는 `keys`·`row_filter`만 받으므로 지금 계약을 유지한다. `/api/verify`처럼 AO 결과를 넘기는 경로는 이 근거로 쓰지 않는다.
2. **위치까지 맞아야 한다.** 표 칸이면 Docraft `provenance`의 행·열이 대상 칸과 같아야 한다. 값만 같고 다른 행에서 읽었다면 열 밀림이나 복제일 수 있다.
3. **정규화 후 정확히 일치해야 한다.** 숫자·날짜 표기만 맞춘 뒤 같은 값이어야 하고, 비슷한 값은 인정하지 않는다.
4. **Docraft가 자신 있어야 한다.** 그 칸의 `field_quality.status`가 `PASS`이고, `issue_codes`에 `approximate_source`·`ambiguous_source`·`row_conflict`·`row_mismatch`가 없어야 한다.
5. **원문 글자가 해당 위치에 있어야 한다.** 원문 대조 결과가 "원문 있음"이어야 하고, "같은 행 다른 칸에서만 발견"이면 복제 의심이라 인정하지 않는다.
6. **칸 종류별로 켠다.** 합성 7종 세트에서 칸 종류(금액·날짜·코드·이름 등)마다 이 규칙의 값 변경 정밀도를 먼저 재고, 기준(예: 99%)을 넘는 종류만 켠다. 설정은 `schema.yaml`의 칸 종류(`kind`) 선언을 쓰고 새 플래그는 만들지 않는다.

반대 방향도 쓴다. Docraft가 AO 원값과 같게 읽으면 원값의 독립 근거가 하나 늘어난 것이다. 이때 원값은 확정하고, 그 칸의 경고는 "다른 판독기도 같게 읽음"으로 남긴다. 이렇게 하면 탐지 장치의 오탐이 검토 대기로 쌓이지 않는다.

구현은 새 판정 엔진을 만들지 않고 기존 `CHANGE_AUDIT_GUARD`를 "독립 출처 묶음 수" 기준으로 다시 정의한다. 계산 채움 허용 칸은 `schema.yaml`의 `computed` 선언을 정책 목록으로 쓴다. 플래그나 함수가 늘지 않는다.

### 6.5 기록

결정마다 `DocumentTrace.changes`에 후보, 근거, 출처 묶음, 결정표 행 번호를 남긴다. 등급이 `ambiguous`·`unresolved`인 칸과 근거 충돌은 개발 고리의 입력이다. 고객 출력의 `harness.ao_value`는 지금처럼 원값을 보존한다.

## 7. 개발 고리 설계

### 7.1 데이터 세 층

| 층 | 내용 | 보정안 에이전트 | 채점 에이전트 |
|---|---|---|---|
| 개발셋 | 노드 재현 표본 중 개발용 분할, 실행 고리 기록, 정답 없는 실문서(정합 일치율용) | 볼 수 있음 | 사용 |
| 숨긴 검증셋 | 노드 재현 표본 검증용 분할(`HoldoutIndex`), 7종 테스트셋 초안 | **볼 수 없음.** 합계 점수만 받음 | 사용 |
| 기준셋 | 합성 7종 세트 중 사람이 확인한 문서(검수 우선순위 상위부터 늘려 감) | **볼 수 없음** | 사용 |

**합성 7종 세트 만들기.** 7종마다 정상 문서와 유형 칸별 오류 문서를 생성기로 만든다. 노드 재현 표본(오류본·대조본 쌍)을 뼈대로 쓰고, 생성 시 개발용·검증용·기준셋으로 나눠 목록 해시를 기록한다. 하네스는 AO 결과가 있어야 돌기 때문에, 세트를 한 번 만들면 배포 담당 세션이 AO 결과·parse와 Docraft `/api/read` 응답을 한 번 모아 캐시로 둔다. 그 뒤 주기는 이 캐시를 재생만 한다. 세트를 새로 만들거나 늘릴 때만 다시 수집한다.

**사람 검수 순서.** 검수는 합성 정답의 정책 확인(인쇄된 값만, 요약 행, 빈칸 표기)이 목적이다. 순서는 ① 채점에서 하네스와 합성 정답이 갈린 칸이 많은 문서, ② 처음 등장한 유형 칸·생성 조합, ③ 정합 일치율이 낮은 문서 순이다. 확인을 마친 문서만 기준셋에 넣고, 확인 전 문서는 개발용·검증용으로만 쓴다.

**실문서 확인.** 합성에만 맞는 보정을 막기 위해, 정답 없는 실문서(데이터셋 7종 폴더 복사본)에 정합 일치율(G6)과 대조본 오탐(G4)을 함께 본다. 실문서 정답 채점은 하지 않는다.

### 7.2 에이전트 역할

| 역할 | 하는 일 | 입력 | 출력 | 권한 |
|---|---|---|---|---|

보정안은 경량 모델이 만들고, 분류와 심사는 상위 모델이 한다. 판단이 필요한 단계가 분류와 심사이기 때문이다([서브에이전트 모델 선택](/home/pilsu/.claude/projects/-home-pilsu-projects-mirae-assets/memory/feedback-subagent-model-choice.md)).

G5 기준이 "악화 0"인 이유: 기준셋은 사람이 정책까지 확인한 문서라, 여기서 악화되면 보정 쪽이 틀렸을 가능성이 가장 크다. 기준셋은 개선을 재는 곳이 아니라 회귀를 막는 곳이고, 개선은 G2·G3에서 잰다.

G2·G3에서 대상 칸이 재현됐는지는 11절의 노드 재현 판정 정책으로 정한다. 재현되지 않은 칸은 효과를 잴 수 없으므로 관문 통과로 보지 않는다.

### 7.4 한 주기의 순서

1. **수집·분류**: 지난 주기 이후 쌓인 실패를 칸별로 묶는다. 묶음마다 실패 수와 영향 칸 수로 순위를 매긴다.
2. **선택**: 상위 칸 최대 3개를 고른다. 정책 결정이 필요한 칸은 사람 대기 목록으로 보낸다.
3. **재현**: 칸마다 개발용 변형을 만든다. 노드 재현 표본에 이미 있으면 그것을 쓴다.
4. **보정안**: 칸마다 `.worktrees/auto-<칸ID>`에서 브랜치를 만든다(`pre-dev` 기준). 칸당 시도는 최대 3회다.
5. **채점·심사**: 관문 G1~G8을 돌린다. 실패하면 이유를 붙여 4로 돌아가고, 3회 실패하면 그 칸을 "자동 보정 불가"로 보고서에 남긴다.
6. **보고**: 통과한 브랜치, 관문 결과표, 사람 확인 목록을 상위 wiki `YYYY-MM-DD-auto-correction-cycle.md`에 남기고 사용자에게 알린다.
7. **병합**: 자동화 단계에 따라 `pre-dev`에 `--no-ff`로 병합하고 워크트리를 정리한다(8절). dev로 올리는 것은 사람이 한다. installer 반영은 30분 묶음 push 규칙을, AWS 확인은 배포 담당 세션 취합을 따른다.

주기는 하루 한 번 또는 사용자 실행으로 시작한다. 실행 수단은 저장된 Workflow 스크립트 하나(`.claude/workflows/self-correct-cycle`)이다. **에이전트 수는 주기당 10개를 넘지 않는다**(2026-10-05 사용자 결정). 배분 예: 수집·분류 1, 재현 1, 칸 3개 × 보정안 1, 채점 1, 심사 1 = 8. 남은 2개는 재시도에 쓴다. 상한에 닿으면 남은 칸은 다음 주기로 넘긴다.

### 7.5 사람에게 올리는 것

| 종류 | 예 | 형식 |
|---|---|---|
| 병합 승인 | 관문을 통과한 보정 브랜치 | 브랜치, 관문 결과표, 바뀐 칸 예시 5건 |
| 정책 결정 | 계산 채움 허용 여부, 서식에 없는 열 처리 | 칸 ID, 영향 문서 수, 선택지 |
| 정답 확인 | 합성 정답과 하네스가 갈린 칸이 많은 문서(7.1 검수 순서) | label_veiwer 번들(검수 우선순위 순서) |
| 자동 보정 불가 | 3회 실패한 칸 | 실패 이유, 필요한 장치 |

정답 확인 결과는 기준셋에 쌓인다. 사람이 검수할 양은 "전체 정답지"에서 "합성 정답과 하네스가 갈린 칸"으로 줄어든다.

### 7.6 채점 조작 방지

- 보정안 에이전트의 워크트리에는 `exp/`, 정답 파일, 숨긴 검증셋 경로가 없다. 이 경로들은 Git 밖이고, 에이전트에게 경로를 알려주지 않는다.
- 채점 에이전트는 주기를 시작할 때 채점 스크립트·정답·검증셋의 SHA-256을 기록하고, 끝날 때 다시 확인한다. 하나라도 다르면 그 주기는 무효다.
- 브랜치 diff가 `tests/`의 기대값이나 `*.answer.json`을 건드리면 G7에서 바로 반려한다.
- 숨긴 검증셋은 합계 점수만 알려준다. 칸 단위 결과는 심사 에이전트와 사람만 본다.

### 7.7 AWS와 외부 호출

- 개발 고리는 로컬 재생만 쓴다. parse 캐시와 함께 **Docraft 응답 캐시**를 만든다. 배포 담당 세션이 AWS에서 `/api/read` 응답을 한 번 모아 두면, 그 뒤에는 실행 고리 6.2~6.4까지 로컬에서 재생할 수 있다.
- 캐시에 없는 다시 읽기가 필요한 보정안은 "AWS 확인 필요"로 표시해 두었다가, 배포 담당의 다음 취합 배포에 한 번에 넣는다.

## 8. 자동화 단계

| 단계 | 에이전트가 할 수 있는 것 | 다음 단계로 가는 조건 |
|---|---|---|
| 0 시범 | 보정안 브랜치와 보고서까지. 병합은 모두 사람 | 시범 칸에서 연속 3주기 동안 사람이 반려한 브랜치가 0 |
| 1 | 선언 파일만 바꾼 보정(동의어·형식·합계 관계 추가)은 관문을 통과하면 `pre-dev`에 자동 병합. 코드 변경은 승인 후 `pre-dev`에 병합 | 단계 1에서 4주 동안 `pre-dev`에서 되돌린 병합 0 |
| 2 | 코드 보정도 G1~G8과 심사를 통과하면 `pre-dev`에 자동 병합. 실행 고리 결정표 변경과 정책 칸은 늘 사람이 결정 | 사용자가 결정 |

**`pre-dev` 운영 (2026-10-05 사용자 결정: 자동 병합은 dev가 아닌 pre-dev).**

- harness-v2·Docraft에 로컬 브랜치 `pre-dev`를 둔다. 주기를 시작할 때 dev를 `pre-dev`에 병합해 따라잡고, 충돌이 나면 그 주기는 보정안을 만들지 않고 충돌만 보고한다.
- 에이전트의 자동 병합은 `pre-dev`까지다. dev로 올리는 것은 사람이 `pre-dev`의 주기 보고서를 보고 `--no-ff`로 한다. 그래서 dev는 늘 사람이 확인한 상태로 남는다.
- dev로 올리기 전에 `pre-dev` 전체로 G1·G5를 한 번 더 돌린다. 보정안끼리 서로 영향을 줄 수 있기 때문이다.
- 문제가 생기면 `pre-dev`에서 해당 병합 커밋만 되돌린다. dev와 installer, 설치 번들에는 영향이 없다.
- installer CI는 dev push에만 반응하므로(`harness-installer/.gitlab-ci.yml`) `pre-dev`는 CI를 띄우지 않는다. `pre-dev`는 원격에 push하지 않는다.

push, 설치 번들 재빌드, NAS 반영, AWS 배포는 어느 단계에서도 자동으로 하지 않는다.

P0-1이 끝나야 P0-2를 할 수 있다. P0-3은 따로 동시에 할 수 있다.

### 노드 재현 판정 정책 추천안 (확인 대기)

1. **재현 기준:** "대조본보다 오류율이 5%p 이상 높음"은 유지하되, 판정 단위가 충분할 때만 쓴다. 조건은 오류본·대조본 각각 20단위 이상, 그리고 단측 Fisher 정확 검정 p<0.05다. 5%p 차이는 단위가 적으면 우연으로도 생긴다. 단위가 부족하면 `not_reproduced`가 아니라 "표본 부족"으로 두고, 생성기가 단위를 더 만든다.
2. **같은 상위 분류의 다른 하위 노드:** 대상 노드의 재현으로 인정하지 않는다. "인접 재현"으로 따로 기록한다. 이 생성 조합은 그 하위 노드의 표본으로 옮겨 쓰고, 대상 노드는 계속 재현 실패로 둔다. 노드가 측정·회귀 단위인데 다른 노드를 재현으로 세면, G2·G3이 엉뚱한 유형의 개선을 대상 칸의 개선으로 셈한다. 그러면 보정안이 잘못된 장치를 고치게 된다.
3. **예외:** 두 하위 노드가 출력만으로 구별되지 않는다고 분류 체계에 적혀 있으면, 그 둘을 한 칸으로 합치는 분류 체계 수정 제안을 사람에게 올린다. 판정기에서 임시로 인정하지 않는다.
