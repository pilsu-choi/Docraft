# 추출·스키마 생성에 페이지 이미지 첨부

`extract()`와 `generate_schema_from_documents()`는 VLM(`qwen/qwen3-vl-32b-instruct`)에 **OCR 텍스트만** 보냈다. 모델은 vision 입력을 받을 수 있는데도 문서를 본 적이 없었고, 표 구조를 PaddleOCR-VL이 만든 텍스트에만 의존했다. 이제 같은 요청에 해당 페이지 이미지를 함께 보낸다.

## 문제: 병합 셀 구조와 한글 오독이 값까지 망가뜨린다

검증 문서(`8a9f90d70e04433cbfd90e21631c5772.png`, 외래 진료비 계산서, 1516×2184)에서 PaddleOCR-VL의 표 출력은 이렇게 어긋난다.

| 증상 | 실제 |
|------|------|
| colspan 누락 | `급여 > 일부 본인부담 > 본인부담금/공단부담금` 2단 병합 헤더가 평평한 열로 뭉개짐 |
| 합계 행이 한 셀로 뭉침 | 열별 합계가 셀 경계 없이 한 칸에 들어감 |
| 한글 오독 | `진찰료` → `진 찰 로`, 주소의 `역삼동` → `억삼동` |

텍스트만 받은 모델은 이 상태에서 **값을 지어낸다**. 열 합계를 `7381`/`17221`로 잘못 계산해 채웠고, 비어 있어야 할 `⑨ 이미 납부한 금액` 칸에 다른 행의 `47300`을 넣었다. 빈칸을 `null`로 두라고 스키마에 적어도 마찬가지였다. 사람이 보면 바로 알 수 있는 오류인데, 근거(grounding)는 그 값이 문서 어딘가에 실제로 적혀 있으면 신뢰도를 1.0으로 매기므로 검토에서도 걸러지지 않는다.

AI 스키마 생성도 같은 텍스트만 보고 설계했다. 망가진 표에서 열 구조를 읽지 못해 금액 열을 **불리언 플래그**로 바꾸는 스키마를 만들어, 애초에 금액을 담을 자리가 없는 결과가 나왔다.

## 검토한 대안

| 대안 | 판단 |
|------|------|
| **페이지 이미지 동봉(채택)** | 이미 vision 모델을 쓰고 있고 provider가 OpenAI 호환 content 배열을 받는다. 파싱 파이프라인·의존성 변경 없이 구조 오류가 사라졌다. 비용은 페이지당 prompt 토큰 +약 2,500 |
| PP-StructureV3로 표 구조 교체 | 실측 기각. 같은 영수증에서 구조가 VL보다 더 망가졌고, 기본 설정에서는 표를 180도 뒤집어 읽었다. 파이프라인이 하나 더 늘어나는데 품질이 더 나쁘다 |
| OCR 텍스트 후처리로 병합 셀 복원 | 헤더 병합 규칙을 문서 종류마다 손으로 써야 한다. 오독(`진 찰 로`)은 후처리로 복구할 수 없다 |
| 프롬프트로 "합계를 직접 계산하지 마라" 지시 | 지어내는 빈도만 줄이고 원인(모델이 표 구조를 모름)은 그대로다 |

## 텍스트 전용 vs 이미지+텍스트

같은 문서·같은 컬럼 충실 스키마(항목별 5개 금액 열 + 열별 합계 + `이미_납부한_금액`)로 비교했다.

| | 텍스트 전용 | 이미지+텍스트 |
|---|---|---|
| 항목명 | 오독 포함 | `진찰료`·`처치 및 수술료`·`수액` 정확 |
| 열별 합계 | `7381` / `17221` (지어냄) | `7300` / `17300` / `40000` (정확) |
| `이미_납부한_금액`(빈칸) | `47300` | `null` |
| 소요 시간 | 14초 | 14초 (동일) |
| prompt 토큰 | 기준 | 페이지당 +약 2,500 |

## 구현

`backend/engine.py`에 이미지 준비 함수 하나를 두고 추출과 스키마 생성이 **같은 함수를 재사용**한다.

* `_data_url(page)` — `fitz` Pixmap으로 페이지를 렌더링해 base64 JPEG data URL을 만든다. 긴 변이 `VISION_MAX_EDGE`(2000px)를 넘지 않도록 축소하고, PDF는 최대 2배까지만 확대한다(A4 기준 약 144dpi). 새 의존성은 없다.
* `_page_images(source, pages)` — `source`(문서 원본 파일 경로)의 1-based 페이지 번호 목록을 data URL 목록으로 바꾼다. 확장자가 PDF·이미지가 아니면(DOCX/XLSX/CSV/TXT/HTML) 빈 목록을 돌려 기존 텍스트 전용 동작을 유지하고, 렌더링 실패는 `warning` 로그만 남기고 역시 빈 목록을 돌린다. 요청당 `VISION_MAX_IMAGES`(4장)를 넘으면 앞 4장만 붙이고 warning을 남긴다.
* `_user(text, images)` — 이미지가 없으면 기존과 똑같은 문자열 content, 있으면 `[{"type":"image_url",…}, …, {"type":"text",…}]` 배열 content를 만든다.

`extract(schema, blocks, source=None)`은 시그니처에 `source`만 추가했다. 페이지 단위 청크(`_page_chunks`)와는 **그 청크에 속한 페이지들의 이미지만** 붙는 방식으로 맞물린다. 블록의 `page`는 파서가 페이지 범위 옵션(`pages`)으로 일부만 파싱했을 때도 `page_map`을 통해 원본 PDF의 1-based 페이지 번호를 유지하므로(`backend/parsers.py`의 `_remote_paddle`·`parse_pdf`), `document[page - 1]`이 언제나 같은 페이지를 가리킨다. `_page_range`와 새 `_pages`는 같은 목록을 공유한다.

system prompt에는 **이미지가 실제로 붙었을 때만** 지시를 덧붙인다.

* 추출: "The page image is attached: read the table structure (merged cells, column headers) from the image, and use the OCR text only as a spelling aid."
* 스키마 생성: 이미지에 보이는 실제 컬럼 헤더 구조(병합 헤더 포함)를 따라 열마다 값 필드를 만들고 열을 불리언 플래그로 바꾸지 말 것.

`generate_schema_from_documents`는 참고 문서마다 앞 2페이지(`VISION_SCHEMA_PAGES`)를 모아 전체 4장까지 붙인다. 호출부(`backend/main.py`)는 이미 `SELECT *`로 읽은 행의 `file_path`를 그대로 넘긴다.

`_provider()`의 `prompt_chars` 계산은 content가 문자열이라고 가정했으므로 `_message_text()`로 고쳤다. 이 함수는 배열 content에서 `text` 부분만 이어 붙이므로 **base64가 로그에 들어가지 않는다**. DEBUG 로그에는 이미지 장 수(`images=N`)만 남는다.

`AI_MODE=local`(`_local_extract`)과 기존 호출부는 그대로 동작한다.

## 설정

| 변수 | 기본값 | 뜻 |
|------|--------|-----|
| `AI_VISION` | `true` | 추출·스키마 생성 요청에 페이지 이미지를 첨부한다. `false`/`0`/`no`/`off`면 기존 텍스트 전용 동작 |

## 비용과 개인정보

* 페이지당 prompt 토큰이 약 2,500 늘어난다. 텍스트만 보낼 때 대비 응답 시간 차이는 관측되지 않았다(14초 동일).
* **문서 페이지 이미지가 외부 AI provider로 전송된다.** OCR 텍스트(사실상 문서 내용 전부)는 이전에도 전송되고 있었지만, 이미지에는 서명·도장·손글씨처럼 텍스트에 없던 정보가 함께 담긴다. on-prem provider가 아닌 환경에서 민감 문서를 다룰 때는 `AI_VISION=false`로 끄거나 provider를 내부망 모델로 두어야 한다. PaddleOCR 자체는 여전히 on-prem이다.

## 검증

단위 테스트 7개를 `tests/test_ai_provider.py`에 추가했다(이미지 문서의 content 배열, `AI_VISION=false`의 문자열 content, PDF 다중 페이지 청크별 페이지 매칭, 이미지 없는 형식, 렌더링 실패 시 텍스트 전용 진행, 스키마 생성 첨부, DEBUG 로그에 base64 없음). 전체 85 passed. `tests/conftest.py`가 개발자 `.env`의 `AI_VISION`에 흔들리지 않도록 값을 고정한다.

실제 provider 호출로 위 영수증을 재검증했다.

1. **추출** — 항목 3개(`진찰료` 4593/10717, `처치 및 수술료` 2788/6504, `수액` 선택진료료 이외 40000), 열별 합계 7300/17300/40000, `이미_납부한_금액` `null`로 기대와 완전히 일치했다. grounding도 `진찰료`와 금액들이 confidence 1.0 + 줄 bbox였다(`[149,414,246,443]` 등).
2. **스키마 생성** — 불리언 플래그가 하나도 없고, 진찰료·입원료·식대·처치 및 수술료 등 항목마다 `patient_share`/`insurance_share` 같은 **열별 number 필드**를 만들었다. 환자 정보·기관 정보·합계 블록도 분리됐다.
3. **생성된 스키마로 추출** — 12초, `consultation_fee` 4593/10717, `treatment_surgery` 2788/6504, `infusion` 40000, `total_medical_fee` 64600(=7300+17300+40000)으로 모두 맞았다.

## 남은 한계

* 이미지는 요청당 4장까지다. 한 청크가 5페이지 이상이면 앞 4장만 붙고 나머지 페이지는 텍스트로만 읽힌다. 페이지가 많은 문서는 `EXTRACT_CHUNK_CHARS`를 줄여 청크를 잘게 나누는 쪽이 낫다.
* JPEG 품질 90·긴 변 2000px로 고정이다. 아주 작은 글씨가 빽빽한 원본에서는 이 축소가 손해일 수 있으나 검증 문서(1516×2184)에서는 영향이 없었다.
* 스키마 생성은 열 구조를 지켰지만 **모든** 열을 만들지는 않았다. 검증에서 `전액 본인부담`·`선택진료료` 열은 항목별 필드로 나오지 않았고 `수액`은 단일 숫자 필드가 됐다. 열 전수를 강제하려면 프롬프트를 더 조이거나 사용자가 스키마를 손봐야 한다.
* 이미지를 붙여도 grounding은 여전히 OCR 텍스트·줄 좌표로만 계산한다([ocr-line-grounding](2026-09-22-ocr-line-grounding.md)). 이미지로만 읽힌 값(OCR 텍스트에 없는 값)은 근거를 찾지 못해 신뢰도가 낮게 나올 수 있다.
