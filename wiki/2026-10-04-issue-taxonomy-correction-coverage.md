## 목적

[Parse와 Extract 이슈 유형 계층 분류](2026-10-03-parse-extract-issue-taxonomy.md)는 오류가 어떤 모습인지를 빠짐없이 나눈다. 이 문서는 그 분류를 **보정 성능**에 연결한다. 목표는 아직 보지 못한 사례가 와도 하네스·Docraft의 보정이 떨어지지 않는 것이다.

이를 위해 다음 순서로 본다.

1. **노드 성격:** 노드마다 연구, 개발, 정책, 평가 중 어떤 일로 풀어야 하는지 나눈다.
2. **일반 보정 방법:** 사례 하나가 아니라 여러 노드를 함께 막는 방법을 서식과 무관한 형태로 정의한다.
3. **현재 구현:** 하네스·Docraft의 실제 장치를 그 방법에 대응시키고, 일반 장치인지, 특정 서식에 묶였는지, 아예 없는지 표시한다.
4. **빈 곳과 우선순위:** 장치가 없거나 서식에 묶인 칸이 새 사례에서 성능이 떨어질 곳이다. 관측 빈도와 업무 심각도로 순서를 정한다.

노드는 측정과 회귀 테스트의 단위이고, 보정 방법은 연구·개발의 단위다. 새 사례가 오면 노드 칸을 찾고, 그 칸을 맡은 일반 방법이 사례를 덮는지 본다. 덮지 못하면 사례별 예외를 넣지 않고 방법을 보완한다.

## 노드 성격

| 성격 | 노드(Depth 3) | 푸는 방식 |
|---|---|---|
| 연구 | `P.WRG.READ`(손글씨·저화질 판독), `P.STR.REL`·`HIER`·`LINK`·`SPLIT`(표·서식 구조 복원), `P.STR.DOC`, `P.WRG.ORDER`, `E.WRG.CTX`, `E.WRG.ATTR`, `E.WRG.ASSIGN.3`, `E.STR.SPLIT.3`(개체 동일성), `E.OVR.GEN`(원문에 없는 값 찾아내기), `E.WRG.HOLD`·`E.MIS.ABST`(보류 판단 보정) | 모델·알고리즘 실험과 비교 평가가 필요하다 |
| 개발 | `P.CON.*`, `E.CON.SCHEMA`·`RANGE`·`EVID`·`DONE`·`PRIV`, `P.OVR.DUP`·`E.OVR.DUP`(중복 탐지), `E.STR.ARRAY`·`ORDER`, `E.MIS.FIELD`·`TARGET`(누락 대조), `E.WRG.ASSIGN.1`·`.2`(열·필드 일관성 검사), `AUX.INPUT`·`AUX.RUN` | 검증기·대조 장치를 만들면 대부분 해결된다. 판단 기준은 스키마 선언에서 읽는다 |
| 정책 | `E.WRG.NORM.4`(원문 유지), `E.OVR.SCOPE.3`(취소·구버전), `E.OVR.GEN.2`(계산값 허용), `E.MIS.TARGET.2`(요약 행 포함), 빈칸·0 표기, 버전 우선순위 | 고객사·업무 결정이 먼저다. 결정은 평가 계약에 버전으로 남긴다 |
| 평가 | `AUX.EVAL`, 정식 키 미확정, 동치 표기 | 정답지·채점기를 고친다. 정답과 출력을 비교하는 코드가 두 벌인 문제를 함께 정리한다 |

한 노드가 두 성격에 걸치면 먼저 해야 하는 쪽에 둔다. 예를 들어 `E.OVR.GEN.2`는 계산값 허용 여부를 정해야(정책) 탐지 기준(개발)이 정해진다.

## 일반 보정 방법

각 방법은 문서 유형·필드 이름을 코드에 두지 않는다. 서식별 지식이 필요하면 **스키마 선언**(필드 종류, 열 종류, 합계 관계, 날짜 선후, 필수 여부, 출력 금지 여부)에서 읽는다. 표의 "선언 없이 동작"은 새 서식에 선언을 추가하기 전에도 기본 방어가 되는지를 뜻한다.

| ID | 방법 | 하는 일 | 주로 막는 노드 | 선언 없이 동작 |
|---|---|---|---|---|
| M1 | 원문 대조 | 출력값마다 근거 위치의 원문 글자(Parse 결과·텍스트 층·이미지 재판독)와 맞는지 확인한다. 원문에 없는 값과 다른 칸에서 복사된 값을 찾는다 | `E.OVR.GEN`·`DUP.2`, `E.WRG.HOLD.1`, `E.CON.EVID`, `P.OVR.*`, `E.WRG.READ` 일부 | 가능 |
| M2 | 사용 범위 대조 | 원문 내용 중 어떤 출력에도 쓰이지 않은 영역·행·글자를 찾는다 | `P.MIS.*`, `E.MIS.TARGET`·`FIELD`·`PART.3` | 가능 |
| M3 | 구조 일관성 | 표 격자, 행·열 정렬, 열마다 값 모양(날짜·금액·코드)의 일관성을 본다. 한 열에 다른 종류의 값이 섞이거나 같은 폭으로 밀린 행을 찾는다 | `E.WRG.ASSIGN.2`, `P.STR.SPLIT`·`REL`·`LINK`, `E.STR.SPLIT`·`ARRAY`·`GROUP`, 오류 패턴 일괄·전치 | 가능(값 모양 추정), 선언이 있으면 더 정확 |
| M4 | 다중 경로 대조 | 서로 다른 경로(외부 추출 결과·Docraft·재판독·텍스트 층)의 값이 다르면 의심 표시한다 | `P.WRG.READ`·`STATE`, `E.WRG.READ`, `E.MIS.PART`, `AUX.INPUT`(텍스트 층 불일치) | 가능 |
| M5 | 계약 제약 | 합계식, 허용 목록, 형식·체크섬, 필드 간·문서 간 제약을 검사한다. 제약 위반은 내용 오류의 탐지 신호로도 쓴다 | `E.CON.RANGE`·`SCHEMA`, 간접적으로 `MIS`·`ASSIGN`·`READ` | 형식·날짜 유효성은 가능, 합계식은 선언 필요 |
| M6 | 변경 감사 | 후처리가 값을 바꿀 때마다 근거 종류를 기록한다. 원문과 달라지는 변경, 계산값의 원문값 확정, 검증 통과만을 근거로 한 확정을 막는다 | `AUX.POST.*`, `E.WRG.NORM.4`, `E.OVR.GEN.2` | 가능 |
| M7 | 단위 경계·중복 | 문서·쪽·표·행 단위의 중복, 합쳐짐·나뉨, 순서를 검사한다 | `P.STR.DOC`·`LINK`, `P.OVR.DUP`, `E.OVR.DUP.1`·`.3`, `E.STR.SPLIT`, `P.WRG.ORDER` | 가능 |
| M8 | 출력 계약 검증 | 스키마·직렬화·완료 상태·출력 금지 값을 검사한다 | `P.CON.*`, `E.CON.SCHEMA`·`DONE`·`PRIV` | 가능 |
| M9 | 입력 무결성 | 디코딩 실패, 프레임·쪽 수, 방향, 축소로 인한 정보 손실을 계측하고 결과에 남긴다 | `AUX.INPUT`, `P.MIS.AREA`, `E.WRG.HOLD.2` | 가능 |
| M10 | 사실 속성 단서 | 부정·의증·과거력·제3자·전언 단서로 확실성·시점·주체를 판단한다 | `E.WRG.ATTR` | 단서 사전은 언어별 데이터 |
| M11 | 후보 보존과 상충 보류 | 후보를 모두 보존하고, 선택 규칙과 근거 등급으로 고르며, 상충하면 보류한다 | `E.WRG.PICK`, `E.MIS.PART.3`, `E.MIS.ABST`·`E.WRG.HOLD` 균형 | 가능 |
| M12 | 문맥 전파 | 머리글·병합칸·라벨·문서 단위 표기(단위·기준일)의 의미를 하위 값에 전파한다 | `P.STR.REL.3`·`.4`, `P.STR.HIER`, `E.WRG.CTX.1`~`.3` | 라벨 동의어는 데이터 |

참조 데이터(`AUX.REF`)와 평가(`AUX.EVAL`)는 보정 방법이 아니라 각각 참조 데이터 관리와 평가 계약 관리로 다룬다.

## 현재 구현 현황

조사 근거: [하네스 장치 목록](evidence/2026-10-04-issue-taxonomy-v4/inv-harness.md)(약 130개), [Docraft 장치 목록](evidence/2026-10-04-issue-taxonomy-v4/inv-docraft.md)(약 120개). 판정의 뜻은 이렇다. **일반**은 서식·필드 이름에 묶이지 않음, **서식 한정**은 코드 상수나 서식별 목록에 등록된 서식·필드에서만 동작, **없음**은 해당 장치가 없음이다.

| 방법 | 하네스 | Docraft | 판정 |
|---|---|---|---|
| M1 원문 대조 | 외부 추출 결과(AO) 값이 쪽에 인쇄돼 있는지 확인하는 일반 장치가 없다. 인쇄되지 않은 합계·급여·건수 같은 특정 항목만 확인한다 | 근거 확인(`ground`)이 일반이지만, OCR 위치가 있다는 증명이지 이미지 판독 증명은 아니다. 근거가 느슨하게 맞으면 통과한다. 라벨 근접 판정은 등록된 라벨 별칭에 의존한다 | 하네스 없음 / Docraft 일반(약함) |
| M2 사용 범위 대조 | 추출 누락 룰 1·2·5가 있다. 필수 키·항목·셀은 yaml이지만 문서 종류별 목록이고, 행 복구는 영수증·세부내역서를 가정한다 | 쪽 실패 표시, 셀 단위 `no_source`만 있다. 행 단위 집계는 없다 | 서식 한정 |
| M3 구조 일관성 | 열 밀림·맞바뀜 보정(N-COLSHIFT·N-SWAP 등)이 영수증 금액 열과 세부내역서 요약 행에 한정된다. 세부내역서 항목 행 맞바뀜은 탐지만 한다. 구조 이상(StructAnomaly)은 로그만 남고 판정에 쓰이지 않는다 | rowmajor 위치 배열과 괘선 격자 재구성은 일반이다. 열 배치 계획은 두 표(영수증·세부내역서 항목내역)에만 있다. 괘선 없는 표의 행 합쳐짐·나뉨 탐지는 없다 | 부분 일반 |
| M4 다중 경로 대조 | 재판독 비교·정합(RR-COMPARE·RR-JOINT)은 일반이다. 다만 재판독 대상 선정이 키 이름 정규식으로 추정한 값 종류에 의존한다 | AO 대비 교차검증 룰 24개는 `/api/verify`에서만 의미가 있다. `/api/read`는 자기 자신과 비교하게 돼 사실상 발동하지 않는다 | 하네스 일반 / Docraft 경로 한정 |
| M5 계약 제약 | 규칙 엔진·식 평가기는 일반이다. 규칙 데이터는 서식별 yaml이다. 약제비영수증(0730)은 규칙 파일이 없어 합계·논리 검증이 없다. 날짜 선후·날짜 유효성·번호 형식·음수 금액 검사가 없다. 문서 간 대조도 없다 | 합계(`FIELD_SUMS`)·날짜 순서(`DATE_ORDER`)·필수 항목이 필드 이름 목록이다 | 엔진 일반, 기준 서식 한정 |
| M6 변경 감사 | 값 변경은 판정 분기 몇 곳에서만 일어나고, 출력에는 repaired·swap·inferred만 반영된다. 원문에 없는 값을 채우는 장치(ENRICH_KCD_05, R-KCD-REVERSE)가 "원문과 달라지는 보정 금지" 방침과 충돌할 수 있다. 검증식 통과로 재판독 값을 채택하는 분기 7은 우연한 통과를 막지 못한다 | 추론값 라벨(`INFERENCE_LABELS`)은 등록 필드에만 붙는다. 근거 문장에서 행을 만드는 장치(G8)가 오히려 인쇄되지 않은 행을 만든다 | 부분, 부작용 위험 |
| M7 단위 경계·중복 | 없다. 해시 멱등은 같은 배치 재접수에만 쓴다 | 청크 경계 중복 1건 처리(B2)만 있다. 같은 표·쪽 반복, 한 쪽에 여러 서류, 쪽 순서는 탐지하지 않는다 | 없음 |
| M8 출력 계약 검증 | 출력 계약 검증은 일반이다. 출력 금지 값 검사는 없다 | JSON 절단 탐지는 일반이다. 깨진 JSON 수리나 내용 오류 재시도는 없다 | 일반, 공개 규칙 없음 |
| M9 입력 무결성 | 없다(UI 입력의 합계 영역 잘림 탐지만 있다) | 방향 판별·재읽기는 일반이다. 다중 프레임은 422로 거부한다. 큰 쪽은 2000px로 축소하고 5쪽부터 이미지 첨부가 조용히 빠지는데, 이를 결과에 표시하지 않는다 | 부분 |
| M10 사실 속성 단서 | 진단서 계열 라벨 정규화(N-DXLABEL)와 체크 그룹에 한정된다 | 진단서 계열 배타 체크 그룹에 한정된다 | 서식 한정 |
| M11 후보 보존과 상충 보류 | 판정 분기표(ARB-TABLE·ROLLUP)는 일반이다 | 재처리의 결정론 후보가 7개 유형에 한정되고, 일반 스키마는 ROI·VLM 단계만 돈다 | 하네스 일반 |
| M12 문맥 전파 | 머리글 인식에 동의어 사전이 없다(HDR 계열 사례). 문맥 상속은 진단서 사고발생일자 산출, 주민번호↔성별·생년월일에 한정된다 | 라벨 보충(G7)이 약 60개 필드의 동의어 표에 의존한다 | 서식 한정 |

정리하면, **판단 엔진(판정 분기, 규칙 엔진, 재판독 비교, rowmajor, 괘선 격자, 출력 계약)은 일반**이다. 그런데 엔진이 쓰는 **판단 기준(필드 이름, 열 이름, 합계식, 라벨 동의어, 필수 목록)은 대부분 코드 상수나 서식별 목록**이다. 그래서 새 서식이나 이름이 바뀐 필드에서는 엔진이 돌아도 기준이 없어 아무것도 막지 못한다. 하드코딩 목록은 하네스 15항목, Docraft 14항목이다(근거 파일의 결론 2 참고).

## 빈 곳과 우선순위

관측 빈도는 관측 기록 906건 대응표에서 원인·후속 ID로 등장한 횟수다(Depth 3, 중복 포함). 예상 시나리오 기록도 일부 섞여 있어 정확한 발생률이 아니라 상대 크기로만 본다.

| 노드(Depth 3) | 관측 등장 | 맡는 방법 | 현재 | 판단 |
|---|---:|---|---|---|
| `E.WRG.ASSIGN` | 97 | M3·M5 | 영수증·세부내역서 열만 | 빈 곳 큼 |
| `E.MIS.FIELD` | 97 | M2·M4 | 서식별 목록 | 빈 곳 큼 |
| `AUX.EVAL` | 88 | 평가 계약 | 비교 코드 두 벌 | 평가 정비 |

| `E.CON.PRIV`, `E.WRG.HOLD` | 0 | M8·M1·M9 | 없음 | 관측 없음, 업무 영향 큼 |

우선순위는 `업무 심각도 × 관측 빈도 × 장치 부재(서식 한정 포함)`로 정했다. 순서대로 하되, 같은 저장소 안 독립 작업은 병렬로 진행한다.

1. **M1 원문 대조를 하네스의 모든 출력값에 적용한다.** 원문에 없는 값(`GEN`)과 복사된 값(`DUP.2`)이 가장 큰 오류군이다. 정답지 59건 자동 분류의 1순위(`E.OVR.DUP.2` 289칸)도 여기에 속한다. Docraft 근거 확인을 판독 증명 수준으로 강화하는 일도 함께 한다.
2. **M3 열 값 모양 일관성을 일반 장치로 만든다.** 열마다 값 모양 분포를 추정해 다른 종류가 섞이거나 같은 폭으로 밀린 행·열을 찾는다. 영수증·세부내역서 전용 보정(N-COLSHIFT·N-SWAP 등)은 이 장치의 선언 파라미터로 옮긴다.
3. **판단 기준을 코드 상수에서 스키마 선언으로 옮긴다.** 필드 종류, 열 종류, 합계 관계, 날짜 선후, 필수 여부, 라벨 동의어를 서식별 선언 한 곳에 두고, 하네스·Docraft가 같은 선언을 읽는다. 새 서식은 선언만 추가하면 M2·M3·M5·M12가 동작한다. 약제비영수증 규칙 부재도 이 단계에서 메운다.
4. **M6 변경 감사로 후처리 부작용을 막는다.** 값을 바꾸는 모든 지점이 공통 기록을 거친다. 원문과 달라지는 변경과 검증 통과만 근거인 확정은 보류로 돌린다. ENRICH_KCD_05·R-KCD-REVERSE·N-UNPRTOT·분기 7·Docraft G8을 먼저 점검한다.
5. **M7 단위 경계·중복과 M9 입력 무결성 계측을 넣는다.** 문서·쪽·표·행 중복, 쪽 순서, 다중 프레임, 축소·이미지 생략을 결과에 표시한다. 장치가 전혀 없는 칸이다.
6. **M5 일반 형식 검사를 넣는다.** 날짜 유효성, 날짜 선후(선언 기반), 번호 형식·체크섬, 음수 금액, 문서 간 대조(`RANGE.4`)를 다룬다.
7. **M8에 공개 규칙(`PRIV`)을 넣고, `HOLD`를 위한 보류 기준(M11)을 정한다.** 관측은 없지만 업무 영향이 크다.

## 새 서식·새 사례에서 성능을 지키는 원칙

- **장치는 일반으로, 서식 지식은 선언으로 둔다.** 코드에 필드 이름·서식 이름을 넣는 보정은 그 서식 밖에서는 아무것도 막지 못한다. 새 보정은 스키마 선언을 읽는 형태로만 추가한다.
- **선언이 없어도 기본 방어선이 동작하게 한다.** M1·M2·M3(값 모양 추정)·M4·M7·M8·M9는 선언 없이도 돌아야 한다. 새 서식이 들어온 첫날에도 원문에 없는 값, 빠진 영역, 밀린 열, 중복, 입력 손실은 잡힌다.
- **값을 바꾸려면 근거가 둘 이상이어야 한다.** 일반 장치는 탐지와 보류를 먼저 한다. 값 변경은 원문 대조와 제약 검사처럼 서로 독립된 근거가 함께 맞을 때만 한다. 검증식 통과 하나로 확정하지 않는다. 원문과 달라지는 보정 금지 방침과도 맞다.
- **오탐도 성능으로 센다.** 노드별로 정탐률과 오탐률을 함께 잰다. 오탐은 과보류(`E.MIS.ABST.2`)나 맞는 값 훼손(`AUX.POST.ALTER`)이 된다.
- **회귀는 노드 단위로 한다.** 각 노드에 실데이터와 합성 변형 테스트를 붙이고, 보정 변경 때마다 다른 노드의 오탐이 늘지 않았는지 함께 본다.

## 측정 방법

- 노드별로 `정탐 / 미탐 / 오탐 / 정상 통과`를 집계한다([분류 문서의 탐지·판정 결과 축](2026-10-03-parse-extract-issue-taxonomy.md)).
- 집계 단위는 label_viewer 자동 분류기(`feat/issue-classify`)의 이슈 기록에 장치 판단(규칙 결과·판정 상태·재판독 여부)을 붙여 만든다. 장치 판단은 하네스 `DocumentTrace`에서 가져온다.
- 새 서식 성능은 "선언 추가 전"과 "선언 추가 후"를 따로 잰다. 선언 추가 전 성능이 기본 방어선의 실력이다.
