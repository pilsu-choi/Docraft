# 운영자 긴급 중지: 문서 잡·in-flight 호출 취소 API

- 날짜: 2026-09-27
- 브랜치: `feat/0927-read-api`
- 워크트리: `.worktrees/read-api`

## 배경

운영자가 긴급 상황에서 Docraft의 작업을 수동으로 멈춰야 한다는 요구다. Docraft에는 두 종류의 작업이 있다.

1. **문서 잡**(`parse`·`extract`): 업로드→파싱→추출을 인라인 스레드 풀 또는 Celery(`backend/worker.py`)로 돌리며, 상태는 Postgres `documents.status`에 남는다.
2. **동기 in-flight 호출** `/api/verify`·`/api/read`: 이벤트 루프 밖 스레드에서 돌고, `threading.Event`(`cancel`)로 취소하면 `verify.Cancelled`를 던져 499를 돌려준다. 진행 건수는 `/api/health`의 `verify_inflight`로 노출된다(`backend/main.py`의 전역 `INFLIGHT`).

기존에는 클라이언트 연결이 끊겼을 때만(요청 쪽에서) 취소할 수 있었고, 운영자가 임의로 잡이나 호출을 멈출 방법이 없었다.

## 설계

### 문서 잡 취소 — `POST /api/documents/{document_id}/cancel`

- `queued`: 잡이 아직 시작하지 않았으므로 바로 `status='canceled'`로 바꾼다.
- `parsing`·`extracting`·`validating`: 이미 스레드(또는 Celery worker)가 실행 중이라 상태를 바로 덮어쓸 수 없다. 대신 새 컬럼 `documents.cancel_requested`(`BOOLEAN DEFAULT FALSE`)를 세운다. `run_parse`·`run_extract`(`backend/main.py`)는 파싱 뒤·추출 뒤·검증 뒤 세 지점에서 `check_cancel(db, document_id)`로 이 플래그를 확인하고, 켜져 있으면 결과를 버리고 `status='canceled'`로 남긴 뒤 즉시 끝낸다. `/api/verify`·`/api/read`의 `_check(cancel)`과 같은 협조적 취소 방식이며, 진행 중인 단일 `parse()`·`engine.extract()` 호출 자체를 중간에 끊지는 않는다.
- Celery 모드(`QUEUE_BACKEND=celery`)면 `jobs.revoke(task_id)`로 아직 브로커 큐에 있는(시작 전) 잡을 함께 제거한다. `task_id`는 큐에 넣을 때(`dispatch()`)의 `AsyncResult.id`를 API 프로세스 메모리(`TASK_IDS` dict)에 잠깐 기억해두는 최선 노력 방식이다 — 큐에 넣는 호출은 항상 API 프로세스에서만 일어나므로 별도 DB 컬럼 없이도 충분하다. revoke가 실패하거나 이미 실행 중이어도 `cancel_requested`가 정확성을 보장한다.
- 이미 끝났거나 취소된 문서(`parsed`·`needs_review`·`completed`·`failed`·`canceled`)는 취소할 잡이 없어 `409`, 없는 문서 id는 `404`다.
- 응답은 `GET /api/documents/{id}`와 같은 문서 표현이다(내부 플래그 `cancel_requested`는 응답에서 뺀다).

### 전체 취소 — `POST /api/admin/cancel-all?confirm=true`

- `confirm=true`가 없으면 되돌릴 수 없는 작업이라 `422`.
- `documents` 테이블에서 `status='queued'`인 행을 모두 `canceled`로, `parsing`·`extracting`·`validating`인 행을 모두 `cancel_requested=TRUE`로 한 번의 요청으로 바꾼다(위 단건 취소와 같은 규칙). 각각 `jobs.revoke`도 시도한다.
- 그 순간 처리 중인 모든 `/api/verify`·`/api/read` 호출의 `cancel` Event도 함께 세운다. 이를 위해 `process_image()`(두 경로가 공유하는 in-flight 처리 헬퍼)가 시작 시 자신의 `cancel` Event를 모듈 전역 `INFLIGHT_EVENTS`(락으로 보호되는 `set`)에 등록하고 끝나면 지운다 — `INFLIGHT` 카운터 바로 옆에 두는 레지스트리다.
- **구분되는 응답 코드**: cancel-all이 세운 Event는 `event.reason = "operator"`를 같이 남긴다. `verify._check`가 `Cancelled(cancel.reason)`으로 이 값을 실어 던지면, 라우트(`cancelled_response()`)가 `exc.args[0] == "operator"`일 때는 `409`("운영자에 의해 작업이 취소되었습니다")를, 그 외(클라이언트 연결 끊김)에는 기존 그대로 `499`를 돌려준다. 하네스나 운영 스크립트가 두 상황을 구분해 처리할 수 있다.
- 응답은 `{"queued_canceled": n, "running_canceled": n, "inflight_canceled": n}` 건수다.

### 스키마·상태

- `documents.cancel_requested BOOLEAN NOT NULL DEFAULT FALSE` 컬럼을 추가했다(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, 기존 `parse_options`와 같은 방식이라 별도 마이그레이션 스크립트가 없다).
- `status`는 `TEXT`라 `CHECK` 제약이 없어 새 값 `canceled`를 추가하는 데 스키마 변경이 필요 없었다.
- 프런트엔드 `frontend/src/types.ts`의 `Status` 유니온과 `frontend/src/ui.tsx`의 `statusText`에 `canceled: '취소됨'`을 더했다(`busy()`·`parsed()`의 상태 목록에는 넣지 않아 취소된 문서는 "처리 중"으로도 "추출 가능"으로도 취급되지 않는다).

## 구현 파일

- `backend/db.py`: `cancel_requested` 컬럼.
- `backend/jobs.py`: `enqueue()`가 백엔드의 결과(Celery `AsyncResult`/inline `Future`)를 돌려주도록 바꾸고, `revoke(task_id)`를 추가.
- `backend/verify.py`: `_check(cancel)`이 `cancel.reason`을 예외에 실어 던진다.
- `backend/main.py`: `RUNNING_STATUSES`/`PROCESSING_STATUSES`(기존 `delete_document`의 리터럴 집합을 재사용하도록 정리), `TASK_IDS`·`dispatch()`·`check_cancel()`, `run_parse`/`run_extract`의 경계 확인, `INFLIGHT_EVENTS`·`_inflight_lock`, `cancelled_response()`, `POST /api/documents/{document_id}/cancel`, `POST /api/admin/cancel-all`.
- `frontend/src/types.ts`, `frontend/src/ui.tsx`: `canceled` 상태 표기.
- `README.md`: API 표에 두 경로 추가, "작업 중지" 절 신설.
- `tests/test_cancel.py`: 신규.
