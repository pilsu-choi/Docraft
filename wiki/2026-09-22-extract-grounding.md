# 추출 프롬프트에 인쇄 항목명·코드 근거 제약 추가

2026-09-22 · 브랜치 `feat/extract-grounding` · 워크트리 `.worktrees/extract-grounding`

## 배경

[통합 평가](2026-09-22-kv-accuracy-integration.md)와 [행 정렬 구현](2026-09-22-kv-row-align.md)이 남긴 1순위 원인은
**모델 추출이 인쇄된 표와 다른 행을 낸다**는 것이었다. 룰 계층에서는 손댈 수 없다 —
`rules._receipt_item`이 파서 표에서 항목 행을 복원할 때 표준 항목 화이트리스트(`RECEIPT_ITEM_NAMES`)를 거치므로,
서식에만 있는 `의학료`·`혈액진단료`·`내복불출치료료` 같은 이름은 애초에 뼈대로 쓰이지 못한다. 남은 지렛대는 프롬프트뿐이다.

## 오류 확인

`data/verify/eval-20260922-201002.json`의 `wrong`을 파싱 캐시(`*.parse.json`)의 표 블록과 대조했다.
영수증+세부내역서 오류 셀 1141개 중 957개(83.9%)가 `항목내역.*`에서 나온다.

| 범주 | 사례 | 규모 |
|---|---|---|
| (a) 인쇄된 이름을 표준 명칭으로 바꿔 씀 | `SA2020010683384…tif`은 25행 전부 `정밀측정`→`장비측정`, `2303314684.jpg`은 `반복처방관리료`→`만성질환관리료`·`척추수치검사`→`직장수지검사` | `항목`+`EDI명칭` rules 기준 348셀(항목내역 오류의 36%) |
| (b) 인쇄되지 않은 행을 지어냄 | `155799374711284.jpg`은 라벨 3행인데 모델 26행(표준 26항목을 통째로 채움), `1549843741259026.jpg`은 라벨 12행 대 모델 20행 | 라벨 있는 20건 중 8건에서 행 수 불일치(최대 +23행), 열 정렬까지 무너져 하위 금액 열로 번짐 |
| (c) 코드 열 혼동 | 세부내역서 parse 캐시 19건 어디에도 `EDI코드`·`원내코드` 리터럴 머리글이 없다. 인쇄된 머리글은 `코드` 10건, `청구코드`·`표준코드`·`코드{수가코드}` 각 1건, 인식 실패 6건 | `원내코드` raw 162셀 → rules 18셀 |

(c)에서 라벨 전수(세부내역서 19건 ≈250행)를 확인하니 **`원내코드`가 채워진 행은 1행뿐**이고 나머지는 모두 `EDI코드`에 들어 있다.
따라서 "코드 열이 하나뿐이면 원내코드"가 아니라 **"코드 열이 하나뿐이면 EDI코드"**가 정답셋과 맞는 규칙이다.

프롬프트 조립은 `engine.extract`가 system 문자열 + `Schema:` JSON + `Source blocks:` 텍스트로 만든다.
표 블록은 파서가 넣은 `<table><tr><td colspan…>` HTML 그대로 실려 행·열과 병합 정보가 남아 있으므로
**직렬화는 손대지 않았다**(회귀 테스트로 고정).

## 모델 재실행 변동 폭 먼저 측정

지침 효과를 재기 전에, 같은 프롬프트·같은 파싱 캐시로 영수증 19건만 다시 추출해 변동 폭을 쟀다
(`--cache-root data/verify/accuracy-20260922/baseline-rerun`, `eval-20260922-203410.json`).

| 집계 | 기준선 | 동일 프롬프트 재실행 | 변동 |
|---|---|---|---|
| all / raw | 2793 (89.8%) | 2873 (92.3%) | **+80** |
| all / rules | 2853 (91.7%) | 2896 (93.1%) | **+43** |
| existing / rules | 933 | 976 | +43 |
| holdout / rules | 1920 | 1920 | **0** |

변동은 기존 36건의 품질 나쁜 TIF 몇 건에 몰려 있다(`SA2019101165425…07.tif` 한 건이 +21).
**holdout 영수증은 재실행에도 흔들리지 않으므로**, holdout이 이번 지침의 신뢰할 수 있는 신호다.
반대로 existing 영수증에서 +43 이하의 개선은 변동 폭 안이라 지침 효과로 볼 수 없다.

## 1차 지침과 그 실패

처음에는 "항목명·명칭·코드를 **인쇄된 글자 그대로** 옮긴다", "읽을 수 없는 칸은 null",
"원내코드는 머리글에 병원 자체 코드임이 드러난 **두 번째 코드 열**이 있을 때만" 까지 넣었다
(`grounded-extract`, `eval-20260922-210156.json`). **순손실**이었다.

| 집계 / rules | 기준선 | 1차 | 판정 |
|---|---|---|---|
| all correct | 7185 (87.81%) | 7159 (87.50%) | **−26** |
| all strict | 6627 (80.99%) | 6467 (79.04%) | **−160** |
| all fp | 330 | 297 | −33 |
| holdout correct | 3881 | 3839 | **−42** |
| holdout strict | 3554 | 3267 | **−287** |

원인을 오류 셀에서 두 가지로 특정했다.

1. **"글자 그대로"가 OCR 잡음까지 충실히 복사한다.** `SA2019040914066`은 `투약및조제료_행위료`를 `필투약및…`으로,
   `SA2019110187887_IT23_6`은 `방사선치료료`를 `밤사선치료료`로 냈다. 정답 라벨은 정제된 표준 표기라 그대로 오답이 된다.
2. **두 번째 코드 열 규칙이 열 밀림을 새로 만들었다.** `2303314684.jpg`은 코드가 `원내코드`로, 명칭이 `EDI코드`로 한 칸씩
   밀려 그 문서 하나에서 코드 오류가 3→44셀이 됐고 `횟수`·`일수`까지 번졌다(holdout 세부내역서 `원내코드` +24, `EDI코드` +20).

## 2차 지침 (채택)

근거가 확인된 부분만 남기고 좁혔다.

| 파일 | 상수·필드 | 내용 |
|---|---|---|
| `backend/doctypes.py` | `GROUND_HINT`(신규) | "문서에 인쇄된 행만 인쇄된 순서대로. 인쇄되지 않은 항목 행을 표준 항목 목록에서 가져와 덧붙이지 않는다. 금액 칸이 모두 비어도 인쇄된 행은 지우지 않는다. 인쇄된 이름이 표준 목록에 없더라도 뜻이 비슷한 표준 이름으로 바꾸지 않는다." |
| | `HINTS` | 항목 행이 서식마다 다른 두 유형(`진료비영수증`·`세부내역서`)의 표 설명에만 `GROUND_HINT`를 덧붙인다. 진단서·소견서 표는 그대로 |
| | `_RECEIPT_ITEM["항목"]` | "표의 항목 칸에 인쇄된 진료 항목 구분명. 표준 목록에 없는 이름(의학료·혈액진단료 등)도 인쇄된 대로 적는다"로 바꿨다. 기존 세분 항목 잇기 규칙은 유지 |
| | `_DETAIL_ITEM["EDI코드"]` | 머리글 후보에 실제 인쇄 표기 `청구코드`·`표준코드`·`수가코드`를 더했다 |
| | `_DETAIL_ITEM["원내코드"]` | "코드 열이 하나뿐이면 그 값은 EDI코드에 적고 여기는 null" |
| | `_DETAIL_ITEM["EDI명칭"]` | "표준 수가 명칭으로 바꾸지 않는다" |
| `backend/engine.py` | `TABLE_NOTE`(신규) | system 지침. "인쇄된 행만 인쇄 순서대로, 없는 행은 만들지 않는다. 표준 이름이 아니어도 인쇄된 항목명을 그대로 둔다" |
| | `extract` | 스키마에 `type: array` 속성이 **있을 때만** `TABLE_NOTE`를 붙인다. 표 없는 일반 프로젝트 스키마는 지침이 그대로다 |

"글자 그대로 복사"와 "읽을 수 없으면 null", 두 번째 코드 열 규칙은 1차에서 손해를 낸 부분이라 넣지 않았다.

파서 표에서 뽑은 항목명 목록을 후보로 프롬프트에 넘기는 안은 **버렸다**. `rules._receipt_table`이 이미 파서 표를
뼈대로 쓰고 있어 역할이 겹치고, 그 뼈대는 표준 화이트리스트를 거치므로 이번에 고치려는 비표준 이름을 담지도 못한다.

## 채택 판정

**채택한다.** 근거와 유보 사항을 함께 적는다.

* 전체 rules 정확도 +50셀(87.81→88.43%), strict +19셀, 오탐 −81(raw 오탐은 459→244로 거의 절반). 순이득이다.
* **영수증 개선은 지침 덕으로 볼 수 없다.** all/rules +38은 동일 프롬프트 재실행 변동 +43보다 작다.
  영수증은 "손해가 없다" 정도로만 읽는다.
* **세부내역서 holdout이 진짜 이득이다.** holdout 영수증이 재실행에 0으로 안정적이었으므로 같은 집합의 세부내역서
  정답 +21·strict +23·오탐 −46은 변동으로 설명되지 않는다. 지침이 겨냥한 (a)(b) 오류가 줄었다는 신호다.
* **나빠진 지표: holdout strict −119셀(75.68→73.15%).** 전량이 영수증이고, 그중 −133이 문서 하나
  `SA2019040914066_3019040922093400.jpg`에서 나온다. 모델이 분류 칸 `선택항목`을 항목명에 붙여
  `선택항목_CT진단료`처럼 냈고, 항목명이 행 키라 `pair_rows`가 7행을 못 맞춰 그 행들의 셀이 통째로 strict 오답이 됐다
  (관용 비교는 부분 포함을 허용해 −1에 그친다). 같은 문서에서 `필투약및…`처럼 OCR 잡음을 복사한 흔적도 남았다.
* 진단서·소견서는 각 −1(변동 수준)이고 오탐은 줄었다. 이 두 유형에는 `TABLE_NOTE`만 적용된다.

### 남은 일

분류 칸(`기본항목`·`선택항목`)을 항목명에 붙이지 말라는 한 줄을 `_RECEIPT_ITEM["항목"]`에 더하면 위 −133은 사라질 가능성이 높다
(`rules._receipt_item`은 이미 "첫 칸은 보통 분류"로 같은 판단을 한다). 이번 작업은 재시도 1회 예산을 2차 지침에 썼으므로
다음 작업으로 넘긴다.

## 테스트

`.venv/bin/python -m pytest tests -q --ignore=tests/ui_*.py` → 289 passed. `tests/test_ai.py`에 추가한 항목:

* `test_extract_grounds_table_rows_in_the_printed_document` — system에 근거 제약이 붙고, 영수증 표 설명에 `GROUND_HINT`가 들어간다.
* `test_extract_leaves_a_schema_without_tables_free_of_the_table_note` — 표 없는 스키마에는 `TABLE_NOTE`가 붙지 않는다(일반 프로젝트 경로 보호).
* `test_extract_sends_table_blocks_as_rows_and_columns` — 표 블록이 행·열 HTML 그대로 프롬프트에 실린다.
* `test_detail_code_columns_route_a_single_printed_code_column_to_edi` — 코드 열이 하나면 EDI코드, 원내코드는 null.
