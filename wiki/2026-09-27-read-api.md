# Docraft를 하네스 읽기 서비스로 만드는 POST /api/read

- 날짜: 2026-09-27
- 브랜치: `feat/0927-read-api`
- 워크트리: `.worktrees/read-api`

## 배경

하네스(harness-v2)는 여러 OCR 결과를 스스로 비교·재분류·최종 채택하는 판단을 맡고, Docraft에는 "읽기"만 요청하고 싶어 한다. 지금까지 하네스가 Docraft를 부르는 유일한 경로는 `POST /api/verify`였는데, 이 경로는 AO 응답을 입력으로 받아 Docraft 추출과 비교하고 `rules.run` 반복 교정과 LLM Judge까지 거쳐 **교정된 AO 형식**을 돌려준다 — 하네스가 재읽기·크롭 재추출(자기 교정)·폴백처럼 AO 비교가 필요 없는 상황에도 AO 형식의 껍데기를 만들어 보내야 했다.

## 구현

### `backend/verify.py`

`run()`의 앞부분(문서 유형·key 검증, 파싱→추출→`rules.apply`)을 세 함수로 뽑았다.

- `resolve_doc_type(doc_type)` — AO 별칭(`doctypes.ALIASES`)을 정규 이름으로 바꾸고 `doctypes.DOC_TYPES`에 있는지 검증한다. 모르면 `ValueError`.
- `resolve_keys(doc_type, keys, *, label="hint_paths")` — key 목록(`hint_paths`·`keys` 공용)을 유형 정의로 검증해 `only` 집합으로 돌려준다. 비어 있으면(`None`·`[]`) `None`(전체). 정의 밖 key는 한 번 경고하고 무시하며, 유효한 key가 하나도 없으면 `ValueError`. `label`은 오류·경고 메시지에 쓰는 필드 이름이다(`/api/verify`는 `"hint_paths"`, `/api/read`는 `"keys"`).
- `read(image, doc_type, only=None, cancel=None) -> (doc_type, docraft_fields, blocks)` — 이미지를 파싱하고 유형 스키마(`only`가 있으면 그 key로 좁힌다)로 추출해 `rules.apply`까지 거친 Docraft 읽기 결과를 돌려준다. AO 비교·교정·Judge는 하지 않는다. `cancel`이 세워지면 추출 직전에 `Cancelled`.

`run()`은 이 세 함수를 그대로 쓰도록 바뀌었을 뿐, AO 비교·`rules.run`·Judge·`_balance` 이후 로직은 손대지 않았다(중복 구현 없음, 회귀 없음은 기존 496개 테스트로 확인).

### `backend/main.py`

- `VERIFY_INFLIGHT` 전역을 `INFLIGHT`로 바꾸고 `/api/verify`·`/api/read`가 함께 늘리고 줄인다. `/api/health`가 내보내는 JSON key는 그대로 `verify_inflight`라 기존 소비자(`deploy/aws/deploy.sh`의 배포 잠금, 테스트)는 바뀌지 않는다 — 이제 두 경로의 합계를 본다.
- `process_image(request, image, fn, *args)` — 업로드 저장·임시파일·다중 페이지(422) 검사·취소·in-flight 계수를 두 라우트가 공유하는 헬퍼. `fn(경로, *args, cancel=cancel)`을 `asyncio.to_thread`로 이벤트 루프 밖에서 돌리고, 클라이언트가 끊기면 `cancel`을 세운다. `HTTPException`(415·413·422)은 그대로 올리고, 그 외는 호출자가 `verify.Cancelled`/`ValueError`/`Exception`으로 나눠 잡는다.
- `POST /api/read` — `doc_type`(필수)·`keys`(선택 JSON 배열)를 `verify.resolve_doc_type`·`resolve_keys`로 검증하고, `verify.read`를 `process_image`로 돌린 뒤 `only`가 있으면 응답 `fields`를 그 key로 한 번 더 좁힌다(`rules.apply`는 항상 유형의 전체 필드를 채워 돌려주므로).

### 계약(변경 없음)

작업 지시의 계약과 실제 구현이 일치한다. 요약:

```
POST /api/read  (multipart, X-API-Key)
  image: 단일 페이지 이미지(/api/verify와 같은 허용 확장자·다중 페이지 422)
  doc_type: 필수, doctypes.ALIASES로 정규화, 모르면 422
  keys: 선택 JSON 배열, 정의 밖 key는 경고 후 무시, 유효 key 0개면 422, 생략시 전체

200 {"doc_type": "<정규화>", "fields": {...}, "elapsed_ms": <int>}
  fields = parse → engine.extract(좁힌 스키마) → rules.apply, 요청 key로 제한. AO·판정 없음.
499 클라이언트 연결 끊김(취소, /api/verify와 같은 방식)
422 ValueError/ParseError, 502 그 외
```

## 후속 과제

- 하네스가 실제로 `/api/read`를 붙인 뒤 재읽기·크롭 재추출·폴백 각각의 응답 형태가 기대와 맞는지 실측 확인이 필요하다(현재는 AWS PaddleOCR·VLM이 뜬 환경에서 실제 이미지로 확인하지 않았다).
- `/api/verify`의 legacy 폴백 경로가 실제로 `/api/read`로 옮겨 가면 `hint_paths`가 남는 이유(룰 엔진이 확정 못 한 필드만 판정)와 `/api/read`의 `keys`(추출 자체를 좁힘)가 서로 다른 목적임을 하네스 쪽에도 알려야 한다.
