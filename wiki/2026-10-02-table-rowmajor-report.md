## 1. 한눈에 보기

**결론: 표를 위치 배열로 읽으면서 열 순서를 문서 인쇄 순서에 맞춰 주면, 표 추출 시간은 약 57% 줄고 정확도는 현행보다 0.6%p 높아진다.**

| 방식 | 표 칸 정확도 | 세부내역서 | 진료비영수증 | 열 뒤바뀜 칸 | 소요 시간 합계 (59건) | 현행 대비 시간 |
|---|---|---|---|---|---|---|
| 현행 (asis) | 89.67% | 80.90% | 99.62% | 31 | 2,303초 | — |
| 위치 배열 그대로 (rowmajor) | 88.81% | 79.53% | 99.39% | 39 | 1,122초 | −51% |
| **최종안: 인쇄 열 순서 + 열 밀림 시 다시 읽기** | **90.27%** | **82.01%** | **99.61%** | **15** | **1,001초** | **−56.5%** |

| 지연 (문서 1건) | 현행 | 최종안 |
|---|---|---|
| 중앙값 | 36.6초 | 14.3초 |
| 상위 10% | 61.4초 | 27.7초 |
| 최대 | 97.4초 | 66.5초 |

- 추가 호출: 59건 중 2건만 현행 방식으로 다시 읽음
- 출력 토큰(모델이 생성하는 글자 양): 평균 약 2,300 → 약 900

## 2. 배경과 목적

- Docraft 표 추출은 행마다 열 이름을 다시 쓰는 방식이라 출력이 길고 느리다. 24행짜리 표가 100~160초 걸려 시간 초과(HTTP 408)가 났고, 처리 시간의 29%가 표 교정 단계였다.
- 위치 배열 방식(rowmajor)은 열 이름을 한 번만 정하고, 각 행은 값만 순서대로 적는다. 출력이 절반으로 줄어 그만큼 빨라진다.
- 목적은 이 방식으로 바꿔도 정확도가 떨어지지 않는지 확인하고, 떨어진다면 그 원인을 없애는 것이다.
- 통과 기준: 정확도 손실 0.1%p 이하, 소요 시간 40% 이상 감소.

## 3. 실험 설정

| 항목 | 내용 |
|---|---|
| 데이터 | 정답지 59건 (세부내역서 29, 진료비영수증 30) |
| 글자 인식 (OCR) | AWS Docraft 서버에서 한 번 실행해 저장한 결과를 모든 방식에 똑같이 사용 |
| 판독 모델 | OpenRouter `qwen3-vl-32b`, 온도 0 (AWS Docraft와 같은 모델) |
| 같게 둔 것 | 이미지, OCR 결과, 모델, 후처리 규칙 |
| 채점 | e2e 채점 기준으로 표 칸만 비교 |
| 범위 | Docraft가 처음 한 번 읽은 결과만 채점. 하네스 중재·재처리를 거친 운영 정확도(59건 99.4%)와는 직접 비교하지 않는다 |
| 호출 수 | OCR 59건(AWS, 1단계만), 판독 모델 약 180건(OpenRouter) |

## 4. 단계별 결과

### 1단계 — 위치 배열 그대로

- 59건 모두 빨라졌다 (중앙값 36.6 → 18.7초).
- 정확도는 0.86%p 떨어졌다. 떨어진 칸의 대부분(93칸)은 세부내역서 1건(`코드2개_급여액_3022033115393304-1.png`)에서 나왔다. 이 문서는 표 전체가 한 열씩 밀렸다.

### 2단계 — 열 밀림 감지와 영수증 양식 맞춤

1. **열 밀림 감지**
   - 세부내역서에서 "단가×투여량×횟수×일수 = 총액" 같은 산식이 맞지 않는 행이 30% 이상이면 현행 방식으로 다시 읽는다.
   - 다시 읽은 문서는 2건이었다. 열이 밀린 문서는 이 조건으로 잡혔고, 다시 읽지 않아도 됐을 문서는 1건이었다.
2. **영수증 양식 맞춤**
   - 진료비영수증 양식 5종의 스키마(`harness-v2/docs/requirements/진료비영수증_양식별_스키마`)를 활용했다.
   - OCR 머리글 낱말로 양식을 판별한다. 30건 중 29건을 판별했고, 잘못 판별한 문서는 없었다.
   - 판별한 양식에 실제로 인쇄된 금액 열만 그 순서대로 모델에 준다.
   - 결과: 영수증 정확도 99.39% → 99.61%, 열 뒤바뀜 2 → 0칸.

### 3단계 — 세부내역서 머리글 순서 맞춤

- **원인 진단**: 위치 배열 방식이 틀린 이유는 하나였다. Docraft가 가진 열 순서는 모든 서식을 합친 공통 순서인데, 실제 문서의 인쇄 순서와 다르다. 모델은 값을 자리 순서대로 채우므로, 문서에 없는 열 자리에 옆 열의 값이 들어간다. 현행은 맞고 위치 배열만 틀린 68칸을 나누면 다음과 같다.

  | 원인 | 칸 수 | 비율 | 설명 |
  |---|---|---|---|
  | 본인부담 ↔ 공단부담 뒤바뀜 | 33 | 49% | 공통 순서의 '급여' 자리가 머리글의 묶음 제목 '급여'와 겹쳐 값이 밀림 |
  | 투여량·횟수·일수 순서 틀림 | 23 | 34% | 공통 순서는 투여량이 단가 앞인데, 실제 인쇄는 일수 뒤 |
  | 기타 | 12 | 17% | 전액본인부담 ↔ 비급여 등, 회전된 스캔 |

- **해결**: OCR 결과에서 머리글 낱말의 가로 위치를 읽어 문서마다 실제 인쇄된 열 순서를 만든다.
  - 오독은 한 글자까지 허용한다 (예: '잎자' → 일자, '충액' → 총액).
  - 붙어 쓴 머리글('수량횟수일수')은 나누고, 떨어진 낱말('급여 구분')은 합친다.
  - 머리글을 4열 미만으로 읽으면 공통 순서로 되돌린다.
  - 판별 결과: 세부내역서 29건 중 25건 판별. 4건(회전 스캔 3, 머리글 인식 실패 1)은 공통 순서를 썼다.
- **결과**: 세부내역서 79.53% → 81.90% (현행 80.90%보다 높음), 열 뒤바뀜 39 → 15칸.

  | 열 | 현행 | 위치 배열 그대로 | 머리글 순서 |
  |---|---|---|---|
  | 투여량 | 92.3% | 86.5% | **94.2%** |
  | 단가 | 90.9% | 88.2% | **92.6%** |
  | 일수 | 93.7% | 92.0% | **94.2%** |
  | 본인·공단부담 | 70.0% | 약 67.7% | **72.3%** |
  | 전액본인부담 | 97.3% | 92.9% | **98.1%** |
  | 총액 | 74.7% | 71.2% | 72.5% |
  | 원내코드 | 93.4% | 94.5% | 89.0% (후퇴, 6절) |

### 열 밀림 감지 기준값 비교 (최종안 위에서)

| 기준 (산식 불일치 행 비율) | 정확도 | 시간 감소 | 다시 읽은 문서 |
|---|---|---|---|
| 감지 안 함 | 90.21% | −59.2% | 0 |
| 0.5 | 90.27% | −57.4% | 1 |
| **0.3 (채택)** | **90.27%** | **−56.5%** | **2** |
| 0.1 | 90.33% | −53.1% | 4 |

영수증 합계 검사(열 합계와 합계 행 비교)는 쓰지 않는다. 합계가 맞지 않는 영수증은 대부분 현행 방식으로 읽어도 맞지 않는다. 다시 읽어도 나아지지 않고 시간만 는다.

## 5. 이식 계획

Docraft에 설정 `TABLE_EXTRACT=rowmajor|asis`를 둔다. 기본값은 rowmajor로 한다(사용자 결정). asis는 설정으로 고를 수 있고, 열 밀림 감지 시 다시 읽는 방식으로도 쓴다.

1. 영수증은 양식 판별, 세부내역서는 머리글 순서로 문서별 열 순서를 정한다. 판별하지 못하면 공통 순서를 쓴다.
2. 위치 배열로 읽은 값을 공통 열 이름으로 되돌린다. 이후 규칙·검증·응답 형식은 바꾸지 않는다.
3. 세부내역서는 산식 불일치 행 비율이 0.3 이상이면 그 표만 현행 방식으로 다시 읽는다.
4. 고객사 내부 모델 서버(vLLM)에서도 같은 방식으로 동작해야 한다.
5. 하네스는 Docraft 응답 형식이 같으므로 변경이 필요 없을 것으로 본다. 이식 후 확인한다.
6. 검증 순서: 오프라인 59건 재실행 → dev 반영 → 배포 담당 세션(6c)을 통한 AWS 확인.

## 6. 한계와 남은 과제

- **표본 크기**: 59건, 1회 실행 결과다. 열 밀림은 실제 사례가 1건뿐이어서 감지 기준 0.3의 근거가 약하다. 표본이 늘면 다시 확인해야 한다.
- **원내코드 후퇴**: 머리글에서 코드 열을 하나만 읽은 서식에서 원내코드 열을 뺀 탓이다 (4.4%p, 21칸). 이식 때 일반 규칙으로 고친다.
- **회전 스캔**: 머리글 위치를 읽지 못해 공통 순서로 처리한다. 결과는 위치 배열 그대로와 같다.
- **영수증 양식 3·5**: 표본이 없어 검증하지 못했다. `선택진료료외만_금액표기` 1건은 값 3칸이 비었고 원인을 찾지 못했다.
- **새 서식**: 머리글 낱말 표가 이번 표본에 맞춰져 있다. 새 서식에서는 판별률을 점검해야 한다.
- **정책 차이**: 세부내역서 정확도가 82%에 머무는 주된 이유는 판독 오류가 아니다. 두 방식 모두 정답지와 범위가 다르다.
  - 급여구분 `열추출` 315칸: 하네스가 채우는 값이다.
  - 소계·합계 행 95행: Docraft가 뽑지 않는 행이다.
- **영수증 개선 요인 분리 안 됨**: 열 배치와 열 설명을 함께 바꿨다. 그래서 둘 중 어느 쪽 덕분인지 나눌 수 없다.

## 7. 용어

| 용어 | 뜻 |
|---|---|
| 현행 (asis) | 행마다 `{"열 이름": 값}` 형태로 쓰게 하는 지금의 Docraft 표 추출 |
| 위치 배열 (rowmajor) | 열 순서를 먼저 정하고, 각 행은 값만 그 순서대로 나열하게 하는 방식 |
| 열 밀림 | 한 칸이 비면서 오른쪽 값들이 한 칸씩 왼쪽 열로 당겨져 들어가는 오류 |
| 열 뒤바뀜 | 정답 값이 같은 행의 다른 열에 들어간 칸 |
| 공통 열 순서 | Docraft가 모든 서식을 합쳐 정해 둔 하나의 열 목록과 순서 |
| 머리글 | 표 맨 위의 열 이름 줄 |
