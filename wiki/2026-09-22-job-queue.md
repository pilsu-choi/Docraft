# 작업 큐(Queue·Worker) 구조 도입

2026-09-22 · 브랜치 `feat/job-queue` · 워크트리 `.worktrees/job-queue`

## 배경

피드백: "배치 검증 지원 - Queue, Worker 구조 지원(redis, celery 등). 단 adaptable 하게. redis, celery는 기존 인프라를 공용으로 활용할 수도 있기에."

이전에는 업로드 파싱, 재파싱, 단건·일괄 추출이 모두 FastAPI `BackgroundTasks`로 API 프로세스 안에서 돌았다. API를 재시작하면 대기 중인 작업이 사라지고, 일괄 추출은 요청 하나 안에서 순차 실행돼 수평 확장이 불가능했다.

## 설계

- `backend/jobs.py` 하나가 디스패치를 맡는다. 진입점은 `enqueue(name, *args)` 하나뿐이다.
  - `TASKS`: `@jobs.task("parse")`, `@jobs.task("extract")`로 `backend/main.py`의 `run_parse`·`run_extract`를 등록한다.
  - `BACKENDS`: `(name, args)`를 받는 함수 dict. `QUEUE_BACKEND`로 고른다. 모르는 값이면 API 기동 시 `RuntimeError`로 즉시 실패한다.
  - `inline`(기본): API 프로세스의 `ThreadPoolExecutor(QUEUE_CONCURRENCY)`에서 실행한다. 추가 의존성이 없다.
  - `celery`: `send_task("<QUEUE_NAME>.<name>", queue=QUEUE_NAME)`. celery는 이 경로에서만 지연 import한다.
- `backend/worker.py`: `backend.main`을 import해 태스크를 등록하고 Celery 앱을 만든다. `python -m backend.worker` 또는 `celery -A backend.worker worker -Q docraft`로 띄운다.
- **enqueue는 트랜잭션 커밋 뒤에** 호출한다. worker가 `queued` 행을 보기 전에 메시지를 받으면 claim이 실패해 문서가 `queued`에 갇히기 때문이다. 업로드·단건 추출·일괄 추출 모두 `with connect()` 블록 밖으로 뺐다.
- **DB claim**: 태스크는 먼저 `UPDATE documents SET status=<parsing|extracting> ... WHERE id=? AND status='queued'`를 실행하고 영향 행이 0이면 경고 로그만 남기고 끝난다. 중복 배달·삭제된 문서는 이렇게 걸러진다(harness-v2의 "DB claim" 교훈).
- **재시도**: Celery 태스크는 `acks_late`, `reject_on_worker_lost`, `prefetch_multiplier=1`이고, `psycopg.OperationalError`·`OSError`(DB/파일 일시 장애)만 지수 backoff로 최대 3회 재시도한다. 파싱·추출 자체의 실패는 기존처럼 문서를 `failed`로 기록하고 사용자가 화면에서 다시 실행한다.
- **공용 인프라 격리**: 큐 이름, 태스크 이름 접두사, redis 키 접두사(`global_keyprefix`)가 모두 `QUEUE_NAME` 하나에서 나온다. 같은 redis·Celery 클러스터를 쓰는 다른 앱과 충돌하지 않는다. 결과 백엔드는 쓰지 않는다(`task_ignore_result`; 정본은 DB).
- `init_db()`에 `pg_advisory_xact_lock`을 추가했다. 빈 DB에서 API와 worker가 동시에 뜨면 `CREATE TABLE IF NOT EXISTS`가 경합해 `UniqueViolation`이 났다(스모크 테스트에서 실제로 재현).

API 계약(202 응답과 본문)은 바뀌지 않았다.

### 배치 진행 상황

새 엔드포인트는 만들지 않았다. 일괄 추출 대상 문서는 `queued → extracting → validating → completed/needs_review/failed`로 `documents` 테이블에 상태가 남고, 프론트는 이미 `GET /api/projects/{id}/documents`를 polling해 상태를 표시한다. 같은 정보를 다른 형태로 내는 `/jobs` API는 중복 개념이 되므로 필요해질 때(작업 이력·소요 시간 테이블) 추가한다.

### 의존성

기본 설치(`requirements.txt`)는 그대로 두고 `requirements-queue.txt`(`celery[redis]==5.6.3`)를 따로 두었다. inline만 쓰는 로컬 개발·테스트는 celery 없이 돈다. Docker 이미지는 API와 worker를 겸하므로 `requirements-queue.txt`를 설치한다.

## 환경변수

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `QUEUE_BACKEND` | `inline` | `inline` 또는 `celery` |
| `QUEUE_CONCURRENCY` | `2` | inline 스레드 수, worker `-c` 값 |
| `QUEUE_NAME` | `docraft` | 큐·태스크 접두사·redis 키 접두사 |
| `CELERY_BROKER_URL` | - | celery일 때 필수 |
| `CELERY_RESULT_BACKEND` | - | 선택(사용하지 않음) |

## 공용 redis/Celery 인프라에 붙이기

1. API와 worker 환경에 `QUEUE_BACKEND=celery`, `CELERY_BROKER_URL=<공용 브로커>`를 설정한다. 필요하면 `QUEUE_NAME`을 조직 규칙에 맞게 바꾼다(예: `docraft-prod`).
2. compose의 `redis` 서비스는 띄우지 않고 `docker compose up -d worker`로 worker만 띄운다. 또는 기존 Celery 운영 방식대로 `celery -A backend.worker worker -Q <QUEUE_NAME>`를 실행한다.
3. worker는 API와 같은 PostgreSQL과 업로드 파일 경로(`DOCRAFT_DATA_DIR`, 공유 볼륨)를 볼 수 있어야 한다. 메시지에는 문서 id만 실린다.

로컬 전용 구성은 `QUEUE_BACKEND=celery docker compose --profile app --profile queue up -d --build`로 redis와 worker를 함께 띄운다.

## 백엔드 추가 방법

`(name, args)`를 받는 함수 하나를 쓰고 `BACKENDS`에 등록한다. 예를 들어 RQ라면:

```python
def _rq(name, args):
    Queue(QUEUE_NAME, connection=Redis.from_url(os.environ["REDIS_URL"])).enqueue(TASKS[name], *args)

BACKENDS["rq"] = _rq
```

worker 쪽은 해당 시스템의 실행기에 `backend.main`을 import한 프로세스를 띄우면 된다. 태스크는 DB claim으로 중복 실행을 막으므로 at-least-once 배달이면 충분하다.

## 검증

- `python -m pytest tests -q --ignore=tests/ui_smoke.py --ignore=tests/ui_preview_layout.py --ignore=tests/ui_project_workspace.py`: 61 passed(3회 반복 동일). 기존 API 테스트는 inline 스레드 풀로 그대로 통과한다.
- `tests/test_jobs.py`: 태스크 등록과 inline 기본값, 알 수 없는 백엔드 거부, 중복 배달이 DB claim에서 무시되는지, celery 백엔드가 `docraft.extract`를 `docraft` 큐로 보내고 `global_keyprefix`·`acks_late`·재시도 설정을 거는지(가짜 celery 모듈) 확인한다.
- 실제 스모크(redis:7 컨테이너 `127.0.0.1:6390`, celery 5.6.3 worker, uvicorn `QUEUE_BACKEND=celery`, `AI_MODE=local`, 임시 schema): 문서 3건 업로드 → worker가 `docraft.parse` 3건 처리 → 일괄 추출 202(`queued` 3) → `docraft.extract` 3건 처리, 3건 모두 `completed`. redis 키는 `docraft:_kombu.binding.*`로만 생성됐다. 이미 파싱된 문서에 parse 메시지를 다시 보내면 worker가 `job skipped, document not queued`로 건너뛰었다. 스모크 후 컨테이너·schema·임시 venv 프로세스를 정리했다.
- Docker 이미지 빌드와 compose `queue` profile 실제 기동은 하지 않았다(`docker compose config`만 확인).

## 남은 한계

- worker가 처리 중 죽으면 메시지는 재배달되지만 문서는 이미 `parsing`/`extracting`이라 claim이 실패해 그 상태에 남는다. 화면의 재파싱·재추출로 복구한다. 오래된 진행 상태를 되돌리는 reaper는 후속이다.
- `queued`는 파싱 대기와 추출 대기에 함께 쓰인다. 파싱 대기 문서에 옛 추출 메시지가 도착하는 경우는 구분하지 못한다(현재 흐름에서는 생기지 않는다).
- inline 백엔드는 API 재시작 시 대기 작업이 사라지는 기존 한계를 그대로 가진다.
- 작업 이력(시작·종료·소요 시간) 테이블과 배치 단위 집계는 없다.
