# Agentic Extract 정확도 97% 개선 작업

## 1. 목표

`harness`와 `docraft` 코드를 전체적으로 분석하고, 이미지에서 정보를 추출하는 과정에서 발생할 수 있는 오류를 최대한 자동으로 찾아내고 고칠 수 있도록 개선해줘.

전체 과정은 다음과 같다.

**이미지 읽기(Parse) → 필요한 값 찾기(Extract) → 값이 맞는지 검사 → 잘못된 값 교정 → 다시 검사 → 최종 확정**

목표는 **최종 Extract 정확도 97% 이상**이다.

단순히 지금 발견된 오류 몇 개만 고치는 것이 아니라, **처음 보는 문서나 처음 발생하는 오류에도 최대한 대응할 수 있는 구조**를 만드는 것이 중요하다.

---

# 2. 가장 중요한 원칙

## 지금 발견된 오류만 하나씩 때우지 말 것

예를 들어 현재 이런 오류가 있다고 해서

- 진단일 오류 → 별도 예외처리
- 질병코드 오류 → 별도 예외처리
- 금액 오류 → 별도 예외처리

처럼 계속 `if/else`를 추가하는 방식으로 만들지 않는다.

가능하면 공통적으로 사용할 수 있는 방법을 만든다.

예를 들어 어떤 값을 추출했다면 공통적으로 다음을 검사할 수 있다.

- 이 값이 원본 이미지에 실제로 있는가?
- 원본의 어느 위치에서 가져온 값인가?
- 올바른 행/열/셀에서 가져왔는가?
- Key와 Value의 위치 관계가 자연스러운가?
- 날짜 필드인데 실제 값도 날짜인가?
- 코드라면 실제 존재하는 코드인가?
- 다른 필드의 값과 서로 모순되지 않는가?

이런 **정상적인 값이 만족해야 할 조건**을 만들어 놓으면 처음 보는 오류도 발견할 가능성이 높아진다.

# 3. 먼저 현재 코드를 분석할 것

바로 코드를 수정하지 말고 `harness`와 `docraft`의 현재 동작부터 정확하게 파악한다.

다음을 확인해줘.

### Parse 단계

이미지를 어떻게 읽고 있는지 확인한다.

- OCR/VLM을 어떻게 호출하는지
- 글자를 어떻게 인식하는지
- 글자의 위치(bbox)를 어떻게 얻는지
- 표를 어떻게 찾는지
- 행/열/셀을 어떻게 구분하는지
- 글자 읽는 순서를 어떻게 정하는지
- 여러 페이지를 어떻게 처리하는지

### Extract 단계

Parse 결과에서 필요한 값을 어떻게 찾는지 확인한다.

예:

```text
진단명 → 위암
질병분류기호 → C16.9
진단일 → 2026-09-01
```

다음을 확인한다.

- Key를 어떻게 찾는지
- Value를 어떻게 찾는지
- Key와 Value를 어떻게 연결하는지
- 표의 여러 행을 어떻게 추출하는지
- 값이 여러 개인 경우 어떻게 처리하는지
- 추출 confidence를 어떻게 계산하는지

### 검증 및 교정

- 추출 결과를 현재 어떻게 검사하는지
- 잘못된 값을 어떻게 발견하는지
- 발견한 오류를 어떻게 수정하는지
- Rule을 어디에서 사용하는지
- LLM/VLM을 어디에서 사용하는지
- 수정한 값을 다시 검사하는지
- 자동으로 판단하기 어려운 경우 어떻게 처리하는지

분석이 끝나면 **현재 전체 처리 흐름과 부족한 부분을 먼저 정리한다.**

# 4. Parse에서 발생할 수 있는 오류를 최대한 정리할 것

Parse는 쉽게 말해서

> "이미지에 무엇이 있고 어디에 있는지 제대로 읽는 과정"

이다.

최소한 다음 오류들을 확인한다.

### 글자를 잘못 읽는 경우

```text
C16.9 → C1G.9
123,500 → 123,50
```

- 글자 누락
- 잘못된 글자 인식
- 불필요한 글자 추가
- 한 글자를 여러 개로 분리
- 여러 글자를 하나로 합침
- 숫자와 영문 혼동
- 띄어쓰기 오류

예:

```text
0 ↔ O
1 ↔ I ↔ l
6 ↔ G
8 ↔ B
```

### 위치를 잘못 잡는 경우

- 글자는 맞는데 bbox 위치가 틀림
- 옆 셀까지 bbox가 포함됨
- 하나의 글자가 여러 bbox로 나뉨
- 서로 다른 글자가 하나의 bbox로 합쳐짐

### 읽는 순서가 틀리는 경우

예를 들어 실제 표가

```text
09/01 | AA123 | 10,000
09/02 | BB456 | 20,000
```

인데

```text
09/01 | BB456 | 10,000
09/02 | AA123 | 20,000
```

처럼 연결되는 경우다.

즉 글자 자체는 모두 정확하지만 **글자 사이의 관계가 틀린 경우도 반드시 잡아야 한다.**

### 표를 잘못 이해하는 경우

- 행이 합쳐짐
- 행이 잘못 나뉨
- 열이 합쳐짐
- 열이 잘못 나뉨
- 값이 옆 열로 밀림
- 병합 셀을 잘못 해석함
- 표 자체를 찾지 못함
- 서로 다른 표를 하나로 합침
- 여러 페이지에 이어진 표를 잘못 연결함

### 이미지 상태가 좋지 않은 경우

- 이미지 회전
- 기울어짐
- 흐림
- 낮은 해상도
- 너무 밝음/어두움
- 그림자
- 문서 일부 잘림
- 도장 겹침
- 서명 겹침
- 손글씨
- 수정 흔적

### 페이지 문제

- 페이지 누락
- 페이지 중복
- 페이지 순서 변경
- 서로 다른 문서가 하나로 섞임

이외에도 실제 코드와 데이터를 분석하면서 새로운 오류 유형이 발견되면 추가한다.

# 5. Extract에서 발생할 수 있는 오류를 최대한 정리할 것

Extract는 쉽게 말해서

> "Parse된 내용 중 어떤 값이 우리가 원하는 값인지 결정하는 과정"

이다.

### Key를 잘못 찾는 경우

예:

```text
우리가 원하는 Key: 진단명

실제 문서:
상병명
병명
주상병
진 단 명
```

이런 표현 차이를 처리하지 못하는 경우다.

### Value를 잘못 찾는 경우

```text
진단명 | 위암
수술명 | 위절제술
```

인데

```text
진단명 = 위절제술
```

로 추출하는 경우다.

### 위치 관계를 잘못 판단하는 경우

- 바로 아래 행의 값을 가져옴
- 옆 열의 값을 가져옴
- 다른 셀의 값을 가져옴
- 다른 표의 값을 가져옴
- 다른 Section의 값을 가져옴

### 같은 Key가 여러 번 나오는 경우

예:

```text
환자정보
성명: 홍길동

의사정보
성명: 김의사
```

어떤 `성명`을 가져와야 하는지 구분해야 한다.

### 값이 여러 개인 경우

예:

```text
주상병: 위암
부상병: 당뇨병
```

- 하나만 추출
- 순서가 바뀜
- 서로 다른 행의 값이 섞임
- 배열 개수가 달라짐

등을 처리해야 한다.

### 비슷한 의미의 필드를 혼동하는 경우

특히 다음을 주의한다.

```text
진단일 ↔ 발병일 ↔ 입원일

진단명 ↔ 수술명

총액 ↔ 본인부담금 ↔ 공단부담금

주상병 ↔ 부상병
```

### 값의 형식이 이상한 경우

- 날짜 필드에 문자열
- 금액 필드에 코드
- 코드 형식 오류
- 소수점 오류
- 음수 처리 오류
- 단위 처리 오류
- 앞자리 0이 사라짐

### 없는 값을 만들어내는 경우

가장 위험한 경우다.

원본에 없는 값을 LLM/VLM이 추측해서 넣으면 안 된다.

**모든 최종 값은 가능하면 원본의 어느 위치에서 나온 값인지 설명할 수 있어야 한다.**

---

# 6. Parse 오류와 Extract 오류를 구분할 것

이 부분은 매우 중요하다.

예를 들어 원본에는

```text
C16.9
```

가 있는데 Parse가

```text
C1G.9
```

로 읽었고 Extract가 그대로

```text
질병코드 = C1G.9
```

를 선택했다면 Extract가 잘못한 것이 아니다.

원인은 Parse다.

따라서 오류가 발생하면 가능한 경우 다음 중 어디에서 문제가 발생했는지 찾는다.

```text
글자를 잘못 읽음
        ↓
문서 구조를 잘못 이해함
        ↓
Key와 Value를 잘못 연결함
        ↓
값의 의미를 잘못 판단함
        ↓
값을 잘못 변환함
        ↓
없는 값을 추측함
```

원인을 찾은 후 **문제가 발생한 단계부터 다시 처리**하도록 한다.

---

# 7. 모든 추출 값은 출처를 추적할 수 있게 할 것

가능하면 최종 결과를 단순히

```json
{
  "질병코드": "C16.9"
}
```

로만 가지고 있지 않는다.

다음과 같은 정보를 같이 유지한다.

```text
값: C16.9

몇 페이지에서 찾았는가?
어떤 글자에서 가져왔는가?
bbox는 어디인가?
어떤 표인가?
몇 번째 행인가?
몇 번째 열인가?
어떤 Key와 연결되었는가?
OCR confidence는 얼마인가?
Extract confidence는 얼마인가?
```

즉 최종 값에 대해

> "왜 C16.9라고 판단했어?"

라고 물었을 때 근거를 추적할 수 있어야 한다.

---

# 8. 추출 결과를 여러 단계로 검사할 것

## 1단계: 원본에 실제로 있는가?

`C16.9`를 추출했다면 원본 이미지에 실제로 해당 값이 있는지 확인한다.

---

## 2단계: 위치가 맞는가?

`질병분류기호`라는 Key와 `C16.9`가 실제로 가까운 위치에 있는지 확인한다.

---

## 3단계: 같은 구조에 있는가?

- 같은 행인가?
- 올바른 셀인가?
- 같은 표인가?
- 같은 Section인가?

를 확인한다.

---

## 4단계: 값의 형식이 맞는가?

예:

```text
진단일 → 날짜인가?
금액 → 숫자인가?
KCD → KCD 코드 형태인가?
```

---

## 5단계: 실제 존재하는 값인가?

Master Data가 있는 경우 반드시 확인한다.

예:

```text
KCD
EDI
약품코드
기관코드
```

---

## 6단계: 다른 값들과 말이 되는가?

예:

```text
진단명 = 위암
질병코드 = C16.9
```

두 값이 서로 맞는지 확인한다.

또는 금액이라면

```text
세부 금액의 합 = 총액
```

같은 관계를 확인한다.

---

## 7단계: 그래도 이상하면 원본 이미지를 다시 본다

Rule만으로 판단하기 어려우면 해당 영역을 이미지에서 잘라 VLM에게 다시 확인시킨다.

처음부터 모든 필드를 VLM으로 다시 검사하지 않는다.

**이상한 값만 골라서 VLM을 사용한다.**

---

# 9. 처음 보는 오류도 발견할 수 있게 만들 것

이번 작업에서 가장 중요한 요구사항이다.

모든 오류를 미리 알고 있을 수는 없다.

따라서 처음 보는 오류라도 다음과 같은 이상 신호가 있으면 잡아낼 수 있어야 한다.

- 원본 위치를 찾을 수 없음
- OCR confidence가 낮음
- Value 후보가 여러 개임
- 서로 다른 방법으로 추출한 결과가 다름
- Key와 Value 위치가 이상함
- 행/열 관계가 이상함
- 데이터 형식이 맞지 않음
- Master Data에 없음
- 다른 Field와 모순됨
- OCR 결과와 원본 이미지가 다르게 보임
- 표의 다른 행들과 구조가 다름
- 문서에 없는 값을 추론함

즉,

**"이 오류를 알고 있는가?"를 기준으로 하지 말고 "정상적인 결과라고 보기 어려운 이유가 있는가?"를 기준으로 탐지한다.**

---

# 10. 오류가 발견되면 단계적으로 교정할 것

바로 VLM에게 전부 맡기지 않는다.

다음 순서로 처리한다.

```text
오류 발견
   ↓
원인 추정
   ↓
Rule로 고칠 수 있는지 확인
   ↓
다시 검사
   ↓
필요하면 해당 영역 다시 Parse/Extract
   ↓
다시 검사
   ↓
그래도 애매하면 해당 영역만 VLM 확인
   ↓
다시 검사
   ↓
필요하면 더 넓은 영역을 VLM 확인
   ↓
다시 검사
   ↓
그래도 확신할 수 없으면 UNRESOLVED
```

VLM이 새로운 값을 제안했다고 바로 정답으로 확정하면 안 된다.

**VLM이 수정한 결과도 다시 Rule/Master/다른 Field와 검증한다.**

---

# 11. 잘못 고치는 것도 오류로 볼 것

예를 들어

```text
원본 OCR: C1G.9
```

를 시스템이

```text
C16.9
```

로 수정했다면 다음 기록을 남긴다.

```text
원래 값: C1G.9
수정 값: C16.9

수정 이유:
KCD Master에 C1G.9가 없음
원본 이미지를 다시 확인하니 C16.9로 보임

수정 후:
KCD Master 확인 PASS
```

그리고 확실하지 않은 경우 억지로 수정하지 않는다.

```text
PASS
CORRECTED
SUSPICIOUS
UNRESOLVED
```

등으로 상태를 구분한다.

**틀린 값을 확신하고 내보내는 것보다 검토가 필요하다고 판단하는 것이 낫다.**

---

# 12. Harness 평가 방식도 개선할 것

정확도 하나만 측정하지 않는다.

최소한 다음을 확인한다.

### 기본 정확도

- 전체 Field 중 몇 개가 정확한가?
- 값을 빠뜨린 비율은 얼마인가?
- 잘못된 값을 넣은 비율은 얼마인가?

### 오류 탐지 능력

- 실제 오류 중 몇 %를 발견했는가?
- Parse 오류를 얼마나 발견했는가?
- Extract 오류를 얼마나 발견했는가?
- 처음 보는 오류를 얼마나 발견했는가?

### 자동 교정 능력

- 발견한 오류 중 몇 %를 자동으로 고쳤는가?
- 자동으로 고친 값 중 몇 %가 실제로 맞았는가?
- 정상 값을 잘못 수정한 경우는 얼마나 되는가?

### 위험한 오류

특히 다음을 별도로 측정한다.

```text
문서에 없는 값을 생성한 경우

틀린 값을 정상이라고 확정한 경우

정상 값을 잘못 교정한 경우
```

---

# 13. 97%의 의미를 명확하게 할 것

단순히

```text
Accuracy >= 97%
```

만 보고 완료 처리하지 않는다.

예를 들어 애매한 값 30%를 전부 `UNRESOLVED`로 보내고 나머지만 계산하면 97%를 쉽게 만들 수 있다.

따라서 최소한 다음을 같이 보고한다.

```text
정확도
자동 처리율
자동 교정 성공률
틀린 값을 정상으로 통과시킨 비율
정상 값을 잘못 수정한 비율
UNRESOLVED 비율
Human Review 비율
```

그리고 **97%가 정확히 어떤 데이터와 어떤 계산 방식으로 나온 숫자인지 명확하게 설명한다.**

# 14. 실제 발생했던 오류는 모두 테스트로 남길 것

지금까지 발견된 오류는 수정하고 끝내지 않는다.

모두 Regression Test로 추가한다.

예를 들어 실제로

```text
AA254가 일자로 잘못 매핑
```

되는 문제가 발생했다면 이를 테스트로 남겨 앞으로 같은 문제가 다시 발생하지 않도록 한다.

새로운 오류를 발견할 때마다

```text
오류 발견
→ 원인 분석
→ 일반적인 해결 방법 구현
→ 테스트 추가
```

순서로 처리한다.

# 15. 일부러 문서를 망가뜨려서 테스트할 것

현재 테스트 데이터에 있는 오류만 잘 처리한다고 일반화가 잘 되는 것은 아니다.

따라서 테스트 데이터를 일부러 변형한다.

예:

```text
글자 한 글자 변경
글자 누락
bbox 이동
행 위치 변경
열 위치 변경
두 행 합치기
한 행 나누기
셀 합치기
셀 나누기
Key 이름 변경
동일 Key 여러 개 추가
Value 삭제
옆 Value와 위치 변경
페이지 순서 변경
표 구조 변경
이미지 회전
Blur 추가
도장/서명 겹침
```

그리고 시스템이 **처음 보는 변형도 이상하다고 감지할 수 있는지** 확인한다.
