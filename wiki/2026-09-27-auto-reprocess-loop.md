## 요청

이전 [Parse·Extract 보강](2026-09-27-parse-extract-quality.md)에서 남은 범용 자동 재처리 루프를 구현한다. 단순 상태 표시를 넘어 원인 추정 → 대상 영역 재처리 → 재검증 → 필요 시 범위 확대 → 확정 또는 검토 요청으로 연결한다.

## 구현 기준

- Docraft에 공통 제어 루프를 두고 기존 Parse·Extract·규칙·검증 기능을 재사용한다. Harness에 별도 유사 루프를 추가하지 않는다.
- 전체 문서를 무제한 재추출하지 않고 의심 필드·영역을 우선한다. 페이지·배열 행·셀의 원래 귀속과 원본 좌표를 유지한다.
- 후보를 바로 덮어쓰지 않는다. 원문·스키마·기존 규칙 검증을 통과한 변경만 채택하고, 나머지 값은 보존한다.
- 시도 횟수·모델 호출·시간 예산을 제한하고 취소·반복 후보·개선 없음·오류를 처리한다.
- 원래 값, 후보, 사유, 처리 단계, 채택/기각, 최종 상태를 결과에서 추적한다. API 로그에 필드 실물을 불필요하게 남기지 않는다.
- 일반 문서와 의료문서 API, Harness 호출의 실제 경로를 연결하고 테스트 및 작은 실제 표본으로 검증한다.

## 진행

Sol 에이전트가 Docraft 공통 루프와 Harness 연동을 나누어 구현하고 Luna 에이전트가 기존 기능·서비스 가용성과 경계 조건을 독립 조사한다. 세 저장소 최신 원격 dev를 확인하고 별도 워크트리를 만들었다. 최종 Docraft 전체 테스트 570건과 Harness 관련 테스트 228건이 통과했다. 독립 최종 검토에서 찾은 일반 스키마 경계 조건 3건을 보완했다. 규칙 재검증을 ROI OCR보다 먼저 수행하도록 순서를 정리했고, 교정된 필드만 기존 API 근거 형식에 병합하도록 회귀 검증했다.

## 결정한 계약

- `remaining_ms`는 초기 읽기를 포함한 남은 요청 시간이다. 0 이하면 호출을 시작하지 않는다. `auto_reprocess=false`는 초기 읽기만 수행하도록 하는 별도 옵션이다.
- 초기 결과를 얻은 뒤 재처리 예산이 소진되면 원래 결과를 보존하고 미해결 상태·중단 사유를 기록한다. 초기 읽기 자체가 만료되면 타임아웃으로 처리한다.
- 재처리의 추가 VLM 호출 예산과 최초 읽기의 호출을 구분한다. 재처리 도중 숨은 표 보정·청크·전송 재시도로 예산을 우회하지 못하게 한다.
- 값이 같아도 새 원문 근거로 의심이 해소되면 검증 진전이다. 값 변경만으로는 진전으로 인정하지 않는다.
- 후보 값의 before/proposed/after 이력은 인증된 Docraft 응답·저장 결과에 보존하고 일반 로그에는 싣지 않는다. Harness에는 필요한 실행 메타를 전달한다.
- 기존 Harness 작업 취소가 이미 실행 중인 동기 HTTP를 즉시 끊는 구조는 아니다. 호출 전후 취소 검사와 서버 예산을 연결하며, 진행 중 네트워크 호출의 즉시 강제 중단을 보장했다고 표현하지 않는다.

## 시험 환경

기존 AWS OCR·Docraft 컨테이너가 healthy인 것을 확인했다. 다른 세션 터널을 수정하지 않고 이번 작업용 터널 18084(OCR-VL), 18085(lines)를 만들었고 둘 다 health HTTP 200을 확인했다. 실제 표본 시험은 이 경로로 수행한다.

## 실제 표본 1차 결과

AWS OCR와 설정된 Qwen VLM을 사용해 기존 독립 silver 35건 중 진단서·진료비영수증·세부내역서 각 1건의 초기 Parse·Extract 캐시를 재처리했다. 원본 3건 모두 후보 채택은 0건이며 기존 값을 보존했다. 각 시도 3회, 추가 모델 호출 1회로 시도 예산에서 중단됐다. 이 시험은 초기 판독을 다시 실행한 전체 API E2E가 아니라 캐시 기반 실제 재처리 replay다.

진단서의 진단일에 의도적 오독을 넣은 별도 시험도 복구되지 않았다. 3단계·모델 2회, 모든 후보 `unverified_candidate`로 거절됐으며 반복 진단 실행은 약 11.1초였다. 추가 진단 결과 모든 단계에서 `distant_label`·exact 근거 부재 때문에 거절된 것으로 확인했다. 의미 라벨 존재 검사는 통과했으나 원문 좌표에서 해당 값과 라벨의 연결이 불확실해 채택 조건을 만족하지 못했다. 자연 표본 정확도 향상이나 의도적 오류 복구를 달성했다고 표시하지 않는다.

비식별 결과는 `Docraft/data/verify/auto-reprocess-20260927/smoke-initial.jsonl`에 보존했다(ignored 데이터 디렉터리). 모델 응답 원문을 포함하던 기존 DEBUG 로깅도 메타데이터만 기록하도록 변경했다.

## 최종 경계 조건 보완

- 일반 3단계 중첩 객체를 표 셀로 오인해 필드 라벨 검증을 건너뛰던 조건을 실제 배열 셀 판별로 제한했다.
- 기존 규칙과 후보 규칙의 차이를 비교할 때 행·열 등의 전체 식별 정보를 포함해 같은 코드의 새 위반을 놓치지 않도록 했다.
- 여러 필드가 순차 교정될 때 앞선 필드의 `CORRECTED` 상태를 유지한다.
- 규칙 재검증 → ROI 파싱 → ROI VLM → 넓은 VLM 순서로 실행한다. 최종 기본 예산은 추가 60초·4단계·추가 VLM 2회이며, 앞서 제시했던 3단계에서 ROI 파싱을 별도 계수하도록 명확히 했다. 목표는 문서 전체를 무제한 재시도하는 것이 아니다.
- 문서가 예산을 공유하고 필드를 기존 순서로 처리하므로 뒤쪽 필드가 시도 기회를 받지 못할 수 있다. 자동 우선순위 최적화는 이번 구현 범위에 포함하지 않는다.

## 최종 자연 표본 replay

최종 4단계 기본값에서 원본 3건을 다시 확인했다. 진단서·진료비영수증·세부내역서 순서로 각각 약 9.8초·3.5초·2.7초, 추가 VLM 호출 1·2·2회였고 모두 시도 4회에서 중단했다. 후보 채택은 0건이며 기존 값을 보존했다. `no_source`·`no_geometry`인 앞쪽 필드가 예산을 사용해 뒤쪽 필드 시도가 제한되는 현상을 trace에서 확인했다. 성능 개선으로 해석하지 않는다. 결과: `Docraft/data/verify/auto-reprocess-20260927/smoke-final.jsonl`.

## 교정 경로 실제 확인

사전에 원문 근거가 명확한 주소 필드를 선정해 의도적 오독을 넣은 별도 시험에서, ROI VLM 후보가 검증되어 `CORRECTED`로 채택됐다. 3단계·VLM 1회, 약 10.6초다. 초기 판독값과 공백·쉼표 정규화 후 같았고 기존 `rules.same` 비교도 참이었다. 문자열 자체는 달라 strict 복구는 아니다. 초기값과 후보 모두 독립 silver 라벨과는 일치하지 않았다. **초기 판독값으로 되돌아오는 실제 기능 경로를 입증했지만, gold/silver 정답 복구나 정확도 향상을 입증한 결과는 아니다.** 결과: `Docraft/data/verify/auto-reprocess-20260927/seed-address-final.jsonl`.

새 gold/silver 라벨을 이번 재처리 구현 단계에서 생성하거나 기존 라벨을 후보에 맞춰 수정하지 않았다.

최종 전체 요청 예산은 `/api/verify`의 후속 AO 판정 호출에도 적용했다. 해당 호출 전후 만료·취소 검사와 잔여 시간 cap을 확인하는 회귀를 포함해 Docraft 전체 570개가 통과했다. 재추출을 다시 대기열에 넣으면 이전 `reprocess` 이력도 초기화한다.
